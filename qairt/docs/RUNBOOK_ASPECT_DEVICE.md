## 2. 备份（约 1 分钟，铁律 2）

```
adb shell pm path <pkg>              # 拉取当前 APK
adb exec-out "run-as <pkg> cat files/models/ZIMAGE/final_qnn_contract.json" > BACKUP.json
```
设备侧另有 `final_qnn_contract.pre-aspect-backup.json`（部署脚本自动生成）。
🔴 上次就是靠这份**设备本地**备份在 30 秒内逐字节复原的。

## 3. 🔴 冒烟测试：先验最大的那个风险（约 3 分钟）

```
ADB=<adb路径> python scripts/aspect_device_smoke.py push
ADB=<adb路径> python scripts/aspect_device_smoke.py run
```

**为什么排在推送全部文件之前**：宿主预测 `part1a` 的 **1:1 图**在五图 context 下
ION = **3320 MiB**，而 unsigned PD 红线是 **3506~3535 MiB**（#57），余量只有 **5.3%**。
其余 15 个图在 1872~3144，安全。整个 mg 形态的成败压在这一个图上，
而它**几秒**就能给出「建得起 context」或 `0x3ea` 硬失败。

| 结果 | 继续 / 中止 |
|---|---|
| 五个图全部 PASS | 🟢 继续第 4 步（mg 形态，12.30 GiB） |
| 任一图报 `0x3ea` / `available PD` | 🔴 **改走 single 形态**：契约用 `final_qnn_contract.single.json`，推送 25.46 GiB。产物已在盘上，不必重建 |
| 报别的错 | ⚠️ 先确认「报错指向的对象是不是我实际验证过的那个」（约束 11·再补），不要照着表面报错去改 |

## 4. 交付（约 8 分钟）

```
bash scripts/deploy_aspect.sh <adb> <pkg> <bin目录> <契约>
adb install -r <apk>
```
部署脚本已堵住四个实测的坑（MSYS 路径改写 / push 失败仍报成功 / `run-as` 建 0 字节文件 /
`adb shell` 非二进制安全），每步校验字节数，**契约最后才换**，sha256 由
`check_deploy_sha.py` 真比对（不是只打印）。

推送量：**mg 形态 8.26 GiB**（去重后 5 个文件）。

## 5. 出图：五个尺寸各一张（约 15 分钟）

后端首次启动约 **205 秒**（新契约 12.30 GiB 的 sha256）。

🟢 **换尺寸不再重启后端**（本轮改动）：Z-Image 的图是 `generate()` 里按请求现取的，
进程与尺寸无关。原本每换一个尺寸要多付 205 秒，五个尺寸省下约 **14 分钟**。

顺序：先 **1024×1024**（回归，必须与第 1 步质量相当），再 1184×896 / 896×1184 /
1280×720 / 720×1280。

🔴🔴 **五次必须用完全相同的 prompt 与种子，否则第 6 步的画质判据无效**
（caption 不同 ⇒ 图不同 ⇒ PSNR 没有意义，而且要等出完图才发现）：

| 字段 | 值 |
|---|---|
| **提示词** | `a cute orange cat sitting on a wooden table, masterpiece, best quality` |
| **随机种子** | `42` |
| 负面提示 | 留空 |

这串 prompt 是从 `p0_experiments/prompt_ids.npy` 用 Qwen tokenizer 反解出来的
（22 token = 14 内容 + 8 chat 模板，与 `mask_r4x3.raw` 里 22 个真 token 一致）。
**宿主的全部 FP32 参考都是用它算的**，见 `cap_r4x3.raw`。
⚠️ 反解要用 `ZImage_Source_Config_Evidence/tokenizer/tokenizer.json`（11.4 MB 的 Qwen 那份）；
`ZImage_QNN_Addendum` 里那份 3.6 MB 的**不是同一个 vocab**，用它解出来是乱码。

| 判据 | |
|---|---|
| 每个尺寸都出图 | 🟢 |
| 图片尺寸 == 请求尺寸、无黑边无拉伸 | 🟢（约束 1：**必须自己打开图看**，不得只看"成功"二字） |
| 1:1 与第 1 步质量相当 | 🟢 无回归 |

## 6. 收尾判据（纯宿主）

🟢 **可以直接拿 app 出的图去比** —— 不必再走 D2 那种「把噪声推到设备、用 `qnn-net-run` 跑」
的路径（那条路每臂 40~70 分钟）。依据是 2026-09-05 的端到端实测（台账 #158）：
app 用 C++ 的 `mt19937` 自己生成噪声，与宿主 `cxx_latents.py` 差 27% 元素、RMS 1.9e-6；
两者各走完整 8 步后 **latents 域 PSNR 121.23 dB、图像域 86.52 dB**
（314 万像素里仅 456 个不同、最大差 1 级）⇒ 相对判据关心的 ~18 dB 量级，**该扰动不存在**。

⇒ **第 5 步出图时，在 UI 里把随机种子设成 42**（与宿主参考对齐），拉回图片后：
```
python scripts/d2_decode_compare.py ...     # 差值口径
```
**判据（沿用 D2，锁定不改）**：`D = PSNR(1:1) − PSNR(新比例) <= 2.0 dB` 🟢。
🔴 **绝对值不得单独作判据**（#143：同一套量化在三个 prompt 上跨度 9 dB）。
