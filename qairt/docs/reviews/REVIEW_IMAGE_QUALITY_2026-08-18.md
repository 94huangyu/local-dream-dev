## 一、当前配置与结果（①实测）

**模型**：Z-Image Turbo，DiT（MatMul + RmsNorm + 残差，**零 Convolution**），W8A16。
**设备**：SM8750 / Hexagon v79 / VTCM 8 MB / 15.4 GB RAM。**SDK**：QAIRT 2.48.0.260626。

**分段**：transformer 拆为 **4 段** `part1a → part1b → part2a → part2b`，全部 **per-row 量化**。
（part2 被迫拆分的原因见 §2.3。）

**成图（本人亲自打开每一张 PNG 确认，非转述）**：

| 配置 | 图像 |
|---|---|
| 三段全基线（per-tensor） | 纯橙/奶油渐变，**零结构** |
| 三段（part1a/1b per-row，part2 基线） | 通体马赛克方块，有横向分界与深色团块，**无任何可辨认物体** |
| **四段全 per-row（当前）** | **清晰橘猫**：虎斑纹、绿眼、胡须、粉鼻、分趾爪、木桌木纹、背景家具层次 |

**app 端实测**：生成 233 s（首步 27.7 s）；`part1a` 4935 ms / `part1b` 1918 ms 每步；
后端冷启动另有约 119 s 的契约 sha256 全量校验（约 11 GB）。

## 二、已确立的机制结论（②，每条附证据）

### 2.1 根因是 HTP 执行，不是量化模型本身

`EXP_PLAN_HTP_INLOOP` 单变量对照：同一份量化模型，**CPU 参考出清晰猫、HTP 出色块**。
`EXP_PLAN_VS_FP32`：CPU 参考跑量化模型距 FP32 仅 **1.1757%**，HTP 距 FP32 **19.2406%**（**16.4 倍**）。
⇒ ②**此前的灾难性图像退化是 HTP-specific；量化本身不足以解释该退化**，
HTP 输出存在远超 CPU quantized reference 的数值偏差。
⚠️ **不写"量化模型完全没问题"**——W8A16 CPU reference 与 FP32 之间仍可能有较小画质差异，
本项目从未单独量过（外部审查 2.1）。

### 2.2 `--use_per_row_quantization` 是目前唯一有效手段

part1b：E_all 19.24% → 7.87%，主体余弦 0.6033 → 0.7986，slope 0.8622 → 1.0435。
part2（拆分后）：单段隔离 E_all 41.24% → 28.52%，主体余弦 0.9089 → 0.9557。
⚠️ `--use_per_channel_quantization` 帮助原文限定 *"convolution-based op weights"*，
本模型零 Conv ⇒ **一直空转**。

### 2.3 容量硬约束（unsigned PD）

`Failed to find available PD ... context size estimate 3652345600`（**不是内存不足**：
同刻 `lowmemorykiller: device has enough memory 8047228Kib`）。
实测红线在 **3506~3535 MB** 之间。per-row 的单段 part2 = 3535 MB **装不下** ⇒ 被迫拆分。
拆分后 part2a 1887 / part2b 1927 MB。

### 2.4 HTP MatMul 在**良态独立探针**中未发现固有精度地板（#30）

单 MatMul 探针，32 测试样本，与主模型同配置：

| K | E_fxp（正确定点） | E_htp | **比值** |
|---|---|---|---|
| 64 | 1.2289% | 1.2301% | **1.00** |
| 1024 | 1.3448% | 1.3597% | **1.01** |
| 3840 | 1.0326% | 1.0327% | **1.00** |

⇒ ②**在当前良态输入、给定 shape 与 encoding 下**，未观察到 HTP MatMul 普遍存在固定精度地板，
也未观察到误差随 K 必然恶化。

🔴 **【2026-08-18 外部审查采纳】原写的"量化配置这条路没有天花板"已删除**——
该推论跨过了 §2.5 那个未解释的矛盾（合成探针比值 1.00 vs 真实 FC 20~230 倍），
在矛盾解释清楚之前不能得出乐观结论。

⚠️ **适用范围（关键，请审查者重点看）**：探针输入是**良态**的 `N(0,σ)`，
**无 massive activation 离群点**；真实模型 `unified` 的 **99.83% 能量集中在前 1%**。
**"单算子正常"不能外推到真实模型。**

### 2.5 与真实模型的矛盾尚未解释（③ 待查）

#39 实测：真实模型里**同为 FC、同为 K=3840**，正确定点误差 0.012~0.19%，**HTP 却 2.72~2.87%**（差 20~230 倍）。
与 2.4 的"单算子比值 1.00"**直接冲突**。

差异只可能来自两处，**尚未分离**：
- **(a) 输入条件数**：探针良态 vs 真实模型极度恶态
- **(b) 图层面效应**：算子融合、中间张量 requant、VTCM 分块

### 2.6 C++ 实现与文本编码/VAE 量化均无害（2026-08-18 新增）

初始噪声**逐字节对齐**后：app（C++ + 量化 TE/VAE） vs PC 在环（Python + FP32 TE/VAE）
= 像素差 **34.26 / 14.74 dB**，**同一只猫、同姿态、同构图**。
⇒ ②**已排除 C++ / TE / VAE 是此前【结构崩坏】的主因。**
🔴 **【外部审查 2.5 采纳】不得写成"剩余画质差距完全来自 transformer"**——
两条流水线仍有 34.26 像素差 / 14.74 dB，**它们对剩余细节画质的贡献尚未隔离**。
隔离方法（暂不优先，但不得提前关闭）：<br>· VAE：固定同一 final latent → FP32 VAE vs 量化 VAE<br>· TE：固定同一 prompt → FP32 embedding vs 量化 embedding 喂同一 transformer

⚠️ 34.26 是真实差异（集中在背景细节），**本实验无法区分它来自"C++ vs Python"还是
"量化 TE/VAE vs FP32"**，未归因给任何一方。

### 2.7 权重与激活是两类东西

| 对象 | 手段 | 被动元素 | 占能量 | 结果 |
|---|---|---|---|---|
| 激活 `unified` | percentile p99.99 | 0.0261% | **98.75%** | ❌ 灾难（主体余弦 0.7986→0.4793） |
| 权重 FC | mse 校准（**可达上界**） | 0.0520% | **1.12%** | ⚪ 无害但仅改善 1.6% |

⇒ **权重不是离群值主导的，激活才是。** 这解释了 per-row（范围不丢）有效、
percentile（砍量程）净损害。
⇒ 连带：**8-bit 下 min-max 往往就是 MSE 最优**（高斯极值 ~3.7σ 已在 8-bit 最优裁剪 ~3.9σ 附近）
⇒ 换权重校准方法基本无空间。

## 三、🔴 最需要外部意见的问题：**没有可信的尺子**

### 3.1 三把标量指标在**一个关键 A/B 对照**中排序与视觉质量相反（①实测）

单变量对照（只换 part2 的量化配置，其余逐字节相同）：

| 指标 | 配置 A（图：马赛克，**认不出物体**） | 配置 B（图：**清晰的猫**） | 指标方向 |
|---|---|---|---|
| step-0 噪声预测相对 L2 | 43.41% | **44.80%** | ❌ 说 B 更差 |
| 对 FP32 参考图平均像素差 | 41.37 | **44.52** | ❌ 说 B 更差 |
| PSNR | 12.46 dB | **11.60 dB** | ❌ 说 B 更差 |

**③未验证解释**：生成模型允许"画对了但内容不同"；且色块的平滑渐变在 L2 上更接近照片均值。
🔴 **【外部审查 2.6 采纳】这原被我标为②，降级为③。** 仅一个 A/B pair **不足以称"反相关"**，
严格能证明的只是：**这三个指标在该对照中排序与视觉相反，故在当前区间不是可靠的单调画质代理**。
**替代解释未排除**：B 可能只是该 seed 在新配置下恰好进入更好的生成轨迹 ⇒ 需多 seed（P2）。

**后果**：原标定「15.99% ⇒ 成图完好、47.07% ⇒ 色块」**只有两个点，且分别来自不同流水线**
（Test B 全 CPU 参考 vs 全 HTP 基线）——**metric 与 configuration 一起变了，是共变不是因果**。
第三个点（44.80% ⇒ 清晰的猫）把这条单调关系打断。

⇒ **所有历史上用 E_all 做过的取舍决策都需复查**，尤其 #56（据此判定"per-row 几乎没有推进"）。

### 3.2 这直接影响后续每一步

没有可信判据，就无法回答"某个量化改动是变好还是变坏"。
**目前唯一可信的判据是人看图**，这不可扩展。

**请审查者重点评估**：
- 用什么替代？（CLIP 图文相似度？FID？LPIPS？在只有单张图、无分布的情况下是否可行？）
- 还是应该**回到中间张量**，但换一个与成图质量已被验证相关的量？
- 「同噪声下与 FP32 逐图比较」是否足够？（见 §4.1）

## 四、后续方案（按优先级，附前提与成本）

### 4.1 【序 0】补一张**可比的** FP32 参考图 —— 纯宿主 10~15 min

**为什么必须先做**：现有 `zimage_fp32_full_pipeline.png` 是用 **numpy 噪声**生成的，
而当前所有设备侧结果用的是 **C++ (`std::mt19937`) 噪声** ⇒ **不可比**。
⇒ **"画质差多少"这个问题现在根本无法回答。**

做法：用已导出的 C++ latents（`p0_experiments/latents_cxx_seed42.raw`）重跑 FP32 全流程。

产出：同噪声下的 FP32 / HTP 逐图对照 ⇒ 才谈得上量化画质差距。

### 4.2 【序 1】重建判别方式（#69）

依赖 4.1。候选（均为 ③ 未验证）：
- 同噪声下与 FP32 的**结构相似度**（SSIM / LPIPS）——比 PSNR 更贴近人眼，但仍是逐像素族
- CLIP 图文相似度——能测"画对了没"，对"画得糙"不敏感
- **多 seed 成对比较**：同噪声下 FP32 与 HTP 各出 N 张，看**成功率**而非单张距离

⚠️ 无论选哪个，**必须先用已知样本验证它能分开"色块 vs 清晰猫"**（约束 8）。

### 4.3 【序 2】解释 2.5 的矛盾：条件数 vs 图层面

**这是当前最有机制价值的一条。** 单算子正确、真实模型差 20~230 倍，二者必居其一：

- **(a) 条件数**：把探针输入换成带 massive activation 离群点的分布重跑
  —— **成本极低**（探针已建好，改输入分布 + 重量化 + 建图 + 设备 <1 min）
- **(b) 图层面**：`--profiling_level detailed` 观察实际执行图；`--vtcm_mb` 调分块（#33/#34）

**建议先做 (a)**，因为它便宜且能直接证伪/证实"恶态输入是主因"。

### 4.4 【序 3】若 (a) 成立 ⇒ 针对 massive activation 的手段

⚠️ 注意已排除项：**通道迁移/SmoothQuant 曾被 #20 关闭**
（理由：主体通道量化表示极限仅 2.90%，而 HTP 73.62% ⇒ 表示不是瓶颈）。
但该关闭理由基于**表示误差**，而 #52 已证明**表示误差不是 HTP 误差的预测量**
⇒ **该关闭论证可能不成立，应重开**（与 #53 同型）。

### 4.5 【未列入但已排除，供审查者核对】

| 路径 | 结论 |
|---|---|
| 权重对称量化 | ❌ 更差（0.6033→0.5507），与官方通用建议相反 |
| 激活 percentile | ❌ 大幅更差（0.7986→0.4793） |
| 权重 mse/sqnr 校准 | ❌ 可达上界仅改善 1.6%（判据线 5%） |
| `--restrict_quantization_steps` | ❌ 只对 A16W16 有效，本项目 A16W8 |
| 图优化级别 O=3 | ❌ Δcos −0.0005 |
| A16W16 / A8W8 | ❌ 内存或精度出局 |
| external weights / spill-fill | ❌ PD 估算一字节未降 |
| SDK 2.28 A/B | 🔻 已降级：原依据"local-dream 用 2.28 跑通"是**相关性非因果**（模型成熟度混淆） |

## 8.2 采纳且**替换我原方案**的两条（审查设计更好）

### (1) Exact-real-FC standalone replay —— 取代我原来的"合成离群输入探针"

我原方案（把探针输入换成带离群点的分布）是**多变量改动**：分布变了、重新校准后 encoding 也变了，
且用的是合成数据。审查方案抽取真实 FC 的**精确输入 / 权重 / encoding，原样复用不重新校准**，
是真正的单变量二分：

- **结果 A**（standalone 仍复现 ~2.8% excess）⇒ 真实数据/encoding/kernel 组合本身即可触发
  ⇒ 再把 exact real input 换成 Gaussian（其余全不变）才可支持"activation 分布是触发变量"
- **结果 B**（standalone 正常）⇒ 转 fusion / inter-op requant / layout / VTCM tiling / scheduling

🔴 **但审查没提的一个前提（我补）**：原样复用 encoding 要靠 `--quantization_overrides` 注入精确
scale/offset，而**本项目从未用它注入过 per-axis(per-row) encoding**（只用过 per-tensor 的
float/对称指定）。若 overrides 不支持 per-axis，则"exact replay"不 exact，结论强度会被削弱。
⇒ **动手前先验证该注入路径（查文档 + 小规模试注入，约 20 分钟），这是 P0-B 的前置门。**

### (2) 8-step teacher-forced + free-running 轨迹拆分 —— 我完全没做过

我们一直只测 **step-0**。审查指出必须分开：
- **teacher-forced**：每步都喂 FP32 参考 latent `x_t`，测**纯局部 HTP 误差**（不被上一步漂移污染）
- **free-running**：各自自由演化，测 `‖x_t^HTP − x_t^FP32‖` 随 t 的**累积漂移**

并且（审查第六节）应记录 **scheduler 更新后的 `Δx_{t+1}`**，而不只是 raw `noise_pred` 的 E_all。

🔴 **这条有一个我们自己的实测支持，审查不知道**：本项目调度器是 `x -= dt·noise`，
而实测 dt 从 step0 的 **−0.0714** 变到 step7 的 **−0.3000**（差 4.2 倍）
⇒ **step-0 的预测误差被最小的 dt 缩放**，它对最终图的影响天然被低估。
这为"44.80% 出猫、43.41% 出马赛克"提供了一个**可检验的机制解释**。

## 8.4 我补充的一条：**FP32 参考本身从未被验证**（审查未提）

用户观察：*"PC 上跑出来的橘猫虽然比手机好，但依然不够完美，不如直接用 Z-Image Turbo 模型跑出来的质量高。"*

⚠️ 先厘清一个事实：**PC 在环那只猫的 transformer 仍然跑在 HTP 上**（只有 TE/VAE 是 FP32），
它不是 FP32 参考，所以"比手机好但不完美"与"HTP 量化掉画质"一致。

但这引出一个**更根本、且从未验证的前提**：
我们所有误差都是以**我们自己的 FP32 流水线**为原点量的，而**该原点从未与官方
diffusers 实现对照过**。调度器、sigma schedule（`shift=3.0`）、timestep 约定（`1 − t/1000`）、
CFG=0、8 步——任何一处与官方不同，FP32 参考本身就已劣化，**下游所有归因都继承该偏差**。

⇒ 新增 **P0-C：同 prompt 同 seed，将我们的 FP32 全流程输出与官方 Z-Image Turbo 实现对照**（纯宿主）。
**若我们的 FP32 已不如官方 ⇒ 优先级整个前移：先修流水线，再谈量化。**

## 8.5 我保留意见的一处

审查第三节主张"不要再寻找一个万能 scalar"——方向同意，
但**分层指标解决的是"诊断"，没有解决"决策"**：接受/否决一个量化配置时仍需要**单一判据**。
⇒ 建议把决策门明确定为 **"多 seed 人工盲测 A/B 成功率"**，
分层指标只用于定位与解释，不用于放行。否则每次取舍又会退回到拿某个 scalar 拍板。
