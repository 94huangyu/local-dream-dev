🔴 **改 markdown 表格的做法纪律（2026-08-24 事故，见台账 #118）**：
1. **只允许「按内容锚定的整行替换 / 整行插入」**（`s.replace(old, new)` + `assert old in s`，或 `lines.insert(i, row)`）。**禁止字符偏移插入**（`s[:k] + x + s[k:]`，`k` 由 `index()+len()` 算出）—— 插入点会落在某一行中间，把两条目并成一行、后一条在渲染时整个消失。
2. **动手前先 `cp` 一份快照**；
3. **「保留原文」必须按字节切片拷贝**（`bak[i:j]`），**不得凭记忆重打**，并断言切片同时存在于快照与新文件；若为渲染需要做 `|` → `\|` 转义，必须断言**反转义后与快照逐字节相同**。

**`lab_dev.wait_done()` 的返回值有三种，调用方必须分别处理**：
`done`（设备在线时确认，可信）／`offline`（**任务可能仍在跑**，需核实产物）／
`lowmem`（告警，**不自动杀进程**，交人决定）。

### 2.1.1 🔴 顶层目标：**与原始模型的一致性**，不是"图好不好"

> 🔴 **2026-08-26 补：改进的「可感知度」依 prompt 而定（实测，见 #131）**
> 同一对配置（per-row vs Clip+FP16）在两种 prompt 下：
> **强约束 prompt**（钉死「橘色的猫」「木头桌子」）：11.93 → **18.67 dB（+6.74）**；
> **弱约束 prompt**（只说「一只猫」「一张垫子」）：12.81 → **14.60 dB（+1.79）**。
> ⇒ 用户真实使用多为弱 prompt ⇒ **可感知的改进约为实验室条件下的 1/4**。
> 但**方向一致且在最显眼物体上可见**（垫子形状/材质命中参考）。⚠️ 每种 prompt 各 1 个样本。
>
> 🔴 **2026-08-26 措辞订正（用户质疑后）：「一致」一词一直用得过满。**
> 当前 **18.67 dB** 的准确含义是「**朝原模型收敛了 6.74 dB，但仍处在换背景/换构图的区间**」，
> **不是**「与原模型一致」。定位依据（外部实测）：FLUX.1-schnell W3A4 = 13.75 dB、
> SDXL W3A4 = 14.88 dB、ImageNet W3A8 = 22.15 dB；我们的 FP32 vs 官方 = 41.61 dB。
> 且主流量化方法（如 Q-Drift）**明确不以逐样本一致为目标** ⇒ 我们追的目标比行业标准更严。
> ⚠️ **两个量化配置彼此差异大是必然的，不构成「无用功」的证据** —— 基准是 FP32 参考，
> 不是上一个量化版本。**同 prompt 同 seed 下两个量化版本出完全不同的图，是预期之内的**
> （2026-08-26 用户在 app 上实测到，已核对：确为同 prompt 同 seed）。
> 但据此判断「哪个更接近原模型」**只能在研究流水线里做**（app 没有 FP32 参考），见 #130。

> 🔴 **2026-08-25 新增硬约束（用户明确要求）：不得再用速度换精度。**
> 下一阶段目标是**提高生图速度**，当前 app 实测约 **250~278 秒**，用户明确表示不满意。
> ⚠️ **已发生的代价**：#111 Clip+FP16 交付后，同 seed 同 prompt 的 app 生图
> 从 **244.9 s 变成 278.0 s（+13.5%）**。当时我用的判据是「远低于 3× 红线」——

## 3. 已确立的关键事实（下结论前先对照）

### 3.1 唯一有刻度的尺子
step-0 噪声预测相对 FP32 的相对 L2（原点 `p0_experiments/vs_fp32/latents_fp32_s0.raw`）：

⚠️ 中间张量 `unified` 集中度 **99.83%** ⇒ 描述它**必须**用主体口径（|a| ≤ p99）。

### 3.2 逐段归因（part2 是支配项）
part2 基线 **41.24%**（主体余弦 0.9089）｜part2 per-row **28.52%**（0.9557）｜CPU 参考上界 15.99%（0.9865）。
上游两段全部改善只贡献约 2.17 pp ⇒ **剩下约 41 pp 是 part2 自己的**。

### 3.3 四条机制结论
1. **`--use_per_row_quantization` 是目前唯一有效手段**（part1b：19.24%→7.87%，cos 0.6033→0.7986）
2. **"细步长有收益"只在动态范围完整保留时成立**：per-row 有收益；activation percentile **净损害**
3. **量化表示误差不是 HTP 误差的预测量**：同一改动 CPU Δcos −0.0014、HTP −0.0526（**37.6 倍**）
4. **权重对称量化更差**（0.6033→0.5507），**与官方通用建议相反**

### 3.5 🔴 宿主消融这一类手段的天花板（#99 导出，2026-08-22）

两个**直接实测**点：

| | 权重 | 激活 | 执行 | E vs FP32 |
|---|---|---|---|---|
| CPU 参考 | 8-bit 量化 | **浮点**（#35：漏 `--enable_cpu_fxp`） | 浮点 | **15.99%** |
| 部署 HTP | 8-bit 量化 per-row | **uFxp_16** | HTP | **44.80%** |

⇒ 两者之间**变了三样**，不是一个变量。正交叠加假设下（**该假设未验证**，仅作量级估算）
15.99% 只占总能量 **12.7%**，其余 **87.3%**（等效 E=41.85%）落在
「**激活 16-bit 量化 + HTP 执行**」这个**尚未分离**的合项里。gamma 8-bit 占 **0.70%**。

🔴 **这两项至今没有被分开过**，原因是 #36：本 SDK 给不出 A16W8 的真定点 CPU 参考
（`error_code=703`，CPU 定点只支持 INT8）。**已知的分离工具只有 #37 的 numpy 定点模拟器。**
⚠️ **不得把这 87.3% 说成「HTP 的问题」**——其中「激活 16-bit 量化」是 A16W8 的固有代价，
不是缺陷。（本条曾于 2026-08-22 写错为「HTP 执行超出部分 87.3%」，当场订正。）

⇒ 对手段选择的实际含义：**「宿主浮点消融」只能直接量到那 12.7%**
（因为它连激活量化都没有）⇒ **再做更多宿主浮点消融的边际价值很低**。

⚠️ **同样不得读成「权重量化工作只值 12.7%」**：#47 per-row 把 part1b 19.24%→7.87%，
远超其表示误差改善所能解释；机制是 #52 的 **37.6 倍敏感度**
⇒ **权重量化改动同时作用于那 87.3%**，只是其杠杆**在宿主浮点上量不出来**。

### 7.0 🔴 设备占用的告知纪律（2026-08-22 犯过，代价 25 分钟 + 惹恼用户）

**手机是用户的，不是我的。占用与释放必须由我明确告知，且状态必须始终一致。**

事故经过：拉完第一批数据后我说了「**可以拔线了**」，**随后又启动了第二轮设备任务，没有重新告知**。
用户按我先前的话拔了线，任务中断。**责任全在我**——而且我事后还问了一句
「是你拔的还是线松了」，那是**毫无意义的追问**，我自己早就让人家拔了。

**规则（无例外）**：

1. **说「可以拔线」= 我承诺此刻起不再占用设备。** 说完之后要再用设备，
   **必须先明确说「请再插上线」并说明要跑多久**，不得默默启动。
2. **启动任何设备任务的同一条消息里，必须写明**：① 要跑多久（或"时长未知"）

3. **每个回合结束前自查**：现在有没有任务在占用设备？用户知道吗？
   两者不一致就必须在本回合说清楚。

### 7.4 Shell / 编码的坑

- `adb shell` 里出现**设备侧绝对路径**必须 `export MSYS_NO_PATHCONV=1`（否则 `/sdcard/x` 被转成 Windows 路径）
- **写 JSON 用 Python `json.dump`，别用 shell heredoc**（反斜杠被折掉 ⇒ 非法 JSON）
- Python heredoc 里**别用 `\n` 转义**（会被展开成真实换行），用 `chr(10)`；**字符串里别嵌双引号**，用「」
- 🔴 **任何命令都别套 `| tail` / `| head`** —— 两个独立理由，第二个更贵：<br>① 缓冲到结束才输出，任务变得不可观测；<br>② **管道的返回码是最后一段的**，`cmd` 失败会被 `tail` 的 rc=0 覆盖 ⇒ **失败伪装成成功**。2026-08-26 实测：`./gradlew assembleBasicDebug | tail -60` 在 `JAVA_HOME is not set`（编译根本没启动）的情况下报 `exited with code 0`。正确写法：`cmd > log 2>&1; rc=$?; …; exit $rc`。<br>**戳穿它的只有产物时间戳**（APK 还停在 6 天前），不是日志内容 —— 同约束 9·补 第 2 条。同类见 #65（`sh()` 吞 adb 错误）、#83、约束 11·再补「报错说谎」
- 🔴 **抓取窗口必须由"已知任务时长"反推，或干脆别用定长 `timeout`**。2026-08-26 连犯两次：生成需 ~4.5 min，我先后开了 20 min（起点太早，到期时任务才刚开始）和 15 min 的定长录制，**两次都在生成中途到期**。正确做法是约束 9·补 第 1 条的阻塞式监听：`until <完成标记出现>; do sleep N; done`，且循环内**同时**检查设备可达（否则掉线会伪装成"还没跑完"）
- 🔴 **编译成功 ≠ 改动进了产物**。`BUILD SUCCESSFUL` 只说明构建图跑通；Gradle 会把大量任务标 `UP-TO-DATE`。**必须比对产物二进制**：从旧 APK 里 `unzip` 出 `lib/arm64-v8a/libstable_diffusion_core.so` 与新编的 `cmp`，不同才算 C++ 改动真的进去了（2026-08-26 实测：19098208 → 19098376 字节）
- SDK 工具会往 GBK 控制台打非法字符 ⇒ `PYTHONIOENCODING=utf-8`（`qairt_tool.py` 已内置）
- 🔴 **经 Bash 工具下发的命令文本里 `\\` 会被吃成 `\`**（2026-09-17 实测三次：Python 源里的 `"\\transformer"` 变成制表符、`\\?\` 长路径前缀变成 `\?\`、连 heredoc 写进 Markdown 的内容也被改）⇒ **含反斜杠的脚本和文档一律先用编辑工具按字面写成文件再执行**；路径拼接用 `os.path.join`
