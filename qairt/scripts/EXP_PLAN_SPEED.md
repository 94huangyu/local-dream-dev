# EXP_PLAN_SPEED —— 提高生图速度（**不得牺牲精度**）

**定稿 2026-08-26。** 上位约束：`MAINLINE.md` §2.1.1「不得用速度换精度」（用户 2026-08-26 定）。
反向同样成立：**本方案的任何手段都不得降低已交付的 18.67 dB 一致性**。

## 一、先看清全貌：278 秒花在哪（已查证，非估算）

| 事实 | 证据 |
|---|---|
| **去噪循环占约 93%** | logcat：step 0 完成 `23:15:15.991`，step 7 完成 `23:19:03.156` ⇒ 7 步 227 s ⇒ **32.4 s/步**；`first_step_time_ms=32728` 与之一致；总 278 s |
| **每一步都重新加载全部四段 context（6.78 GB）** | `PipelineZImage.hpp` 的 `for (step...)` 循环体内做 `loadGraph(part1a/1b)` → 释放 → `loadGraph(part2a)` → `loadGraph(part2b)`。8 步 ⇒ 累计加载约 **54 GB** |
| 这样做的**原因**是内存 | 同文件注释：三段全驻留实测 **~7.3 GB**，被设备低内存杀手干掉；part1a+1b（~3.84 GB）是"已证明安全"的包线 |
| **DVFS 已是最激进档** | `QnnModel.hpp`：`DCVS_V3` + `PERFORMANCE_MODE` + bus/core voltage corner 全部 `MAX` + `sleepDisable=1` + RPC 低延迟 ⇒ **没有白拿的性能档** |
| **步数已到下限** | `Config.hpp: zimage_turbo_steps = 8`，`RequestParser` 强制、`PipelineZImage` 拒绝其他值 |
| **砍浮点换速度不可行** | #128：只钳位不带锥只值 1.44 pp ⇒ 435 个锥张量是承重的 |

⇒ **唯一的大杠杆是「把 `loadGraph` 提出步循环」**，代价是峰值内存上升。

## 二、第一步只做测量，不改代码

**在改任何东西之前，必须先知道 32.4 s/步 里有多少是加载、多少是计算。**
不知道这个比例就无法判断"提出循环"值不值得，也无法设验收标准。

**方法**（工具自带，`qnn-net-run --help` 已核对）：

```
qnn-net-run --retrieve_context <seg>.bin --num_inferences N ...
```
同一段分别跑 `N=1` 与 `N=5`：
- **斜率**（(T5−T1)/4）= 纯计算时间/次
- **截距**（T1 − 斜率）= 加载 + 初始化时间

对 **part1a**（2.37 GB，最大）与 **part2b**（1.49 GB）各做一次，得到加载时间与体积的关系。

**成本**：约 15 分钟设备时间，**不改任何代码、不重建任何产物**。

### 判据（事前锁定）

| 加载占比 | 结论与动作 |
|---|---|
| **≥ 40%** | 🟢 提出循环的上限收益 ≥ 每步 13 s ⇒ **值得做**，进入 §三 |
| 15% ~ 40% | 🟡 收益中等，与内存风险一起权衡 |
| **< 15%** | ❌ 加载不是瓶颈 ⇒ **放弃这条**，转 §四的备选 |

### 🔴 实测结果（2026-08-26，四段全测，`scripts/speed_split.py`）

| 段 | T(N=1) | T(N=5) | 计算/次 | **加载+初始化** |
|---|---|---|---|---|
| part1a（2.37 GB） | 32.1s | 145.7s | 28.4s | **3.7s** |
| part1b | 18.7s | 81.6s | 15.7s | **3.0s** |
| part2a | 18.7s | 81.0s | 15.6s | **3.1s** |
| part2b（1.49 GB） | 18.1s | 77.0s | 14.7s | **3.4s** |
| **每步四段合计** | | | 74.4s | **13.2s** |

### 🔴🔴 判据的**操作化**写错了（约束 8 —— 本方案定稿时就该验证的）

脚本原本把「加载占比」的分母取成 `qnn-net-run` 的**总耗时**，得出 11.5~18.6% ⇒ ❌ 放弃。
**这个分母是错的**，且**理由与结果无关、事前即可论证**：

> 四段「计算」合计 **74.4 s**，而 app 跑完一整步只要 **32.4 s**。
> `qnn-net-run` 的单次耗时里含着**把输出张量写盘**（part1a 有 8 个输出、100+ MB），
> **app 完全不付这个成本**。⇒ `qnn-net-run` 的总耗时**本来就不是** app 的每步耗时。

**正确的分母是 app 实测的 32.4 s/步**（§一，logcat 证据）：

```
加载 13.2 s ÷ 每步 32.4 s ≈ 41%   ⇒  🟢（判据线 ≥40%）
```

⚠️ **阈值没有改，改的是被测量的定义。** 判据表原样保留在上面，未事后修改。

**上限收益**：13.2 s/步 × 7 步 ≈ **92 秒** ⇒ 278 s → 约 **186 s（−33%）**，且**完全不动精度**。
（截距是**热缓存**下的值：N=5 那次跑之前文件已被 N=1 带进 page cache，
与 app 每步反复加载同一文件的情形一致 ⇒ 可迁移。）

⚠️ 未测的量：**加载时间与体积不成正比**（2.37 GB 的 part1a 只比 1.49 GB 的 part2b 多 0.3 s）
⇒ 固定开销（图反序列化、HTP 上下文准备）占大头，**方案 A 的收益不能按体积比例折算**。

## 三、🟢 判定通过 ⇒ **待办：把 loadGraph 提出步循环**（方案已定稿，尚未执行）

| 方案 | 峰值驻留（估算，需实测） | 每步省下的加载 |
|---|---|---|
| 现状 | ~3.84 GB | 0 |

⚠️ 方案 B 逼近 #16 实测的 7300 MB 杀线 ⇒ **必须先在设备上实测驻留峰值**，
用 `ps -o RSS` + `dumpsys meminfo` 双测，**不得只看一个数**。

🔴 **验收必须同时满足**：① 生图时间下降；② **三层指标与当前完全一致**
（同噪声同 caption，L1/L2/L3 逐位或在装置噪声内）；③ 连续生成 3 张不被 LMK 杀掉。

| 候选 | 精度风险 | 说明 |

## 五、纪律

- 每个候选都必须同时报**速度**与**三层一致性**，缺一不可（§2.1.1）。
- 结论措辞：`qnn-net-run` 的离线计时是**单段离线执行**，不得直接等同于 app 内的每步耗时；
  两者的差异（进程启动、上下文复用）必须在引用时说明。
