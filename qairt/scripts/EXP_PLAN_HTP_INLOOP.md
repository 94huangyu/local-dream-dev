# EXP_PLAN_HTP_INLOOP —— 在 HTP 上重做 Test B（把"47% 差异"变成"能不能毁图"）

定稿时间：2026-08-15（执行前定稿，判据不得事后修改）
前置：`EXP_PLAN_HTP_VS_CPU_B1B2.md`（级联噪声预测 HTP vs CPU 差 **47.07%**，约为标定点 3 倍）
主线归属：A → 假设 C（当前唯一候选）

## 0. 为什么必须做这一步

上一轮拿到的是**差异**，不是**根因**。项目纪律（CLAUDE.md 约束 2、MAINLINE 规则 1）要求：
**找到异常后必须单独论证"它能否造成观察到的现象"。**

本项目已有一个现成的、已定稿的实验框架可以直接闭环——**Test B**：
它用 CPU 参考跑同样的量化 transformer，其余全 FP32，出的是**清晰的猫**（PSNR 23.89 dB）。
**只把执行后端从 SNPE CPU 换成设备 HTP，其余一个字节都不改**，看出什么图。
这是同一框架内的**单变量对照**，也是本项目"级别 2 验证"的标准用法。

## 1. 预期结果（假设）

**H-inloop**：HTP 在环出图 ≈ 橙色无定形色块 ⇒ 假设 C 被坐实为根因。

零假设：出图 ≈ 清晰的猫 ⇒ 47% 的噪声预测差异**不足以毁图**
⇒ C 被否定为根因，假设树全部节点排除，必须回顶层重提假设。

## 2. 实现路径

复制 `testB_hybrid_pipeline.py` 的全部流程，**只替换 `snpe_run` 为 `htp_run`**：

```
分词 + FP32 文本编码(onnxruntime)           <- 与 Test B 逐字节相同
[8 步: part1a(HTP) -> part1b(HTP) -> part2(HTP) -> FlowMatch 调度器(FP32,numpy)]
FP32 VAE 解码(onnxruntime) -> PNG
```

同 prompt、同 seed(42)、同 8 步、同调度器系数、同 VAE。

`htp_run`：把输入 `.raw` 推到设备 → `qnn-net-run --retrieve_context <part>.bin
--backend libQnnHtp.so`（**非 native 模式**，float32 进出）→ 拉回输出。
**段间中间张量全程留在设备上**，每步只推 `latents`(1MB)+`timestep`(4B)、只拉 `latents`(1MB)，
避免每步 130MB 的无谓往返。`caption` / `cap_pad_mask` 全程不变，只推一次。

`.bin` 用已验证与设备 app 副本 **md5 相同**的那三份（part1a/1b/2）。

## 3. 验收标准（判据，事后不得修改）

**判据 0（执行有效性）**：每步每段的输出元素数必须等于契约声明；
最终 `latents` 必须是 262,144 个 float32。任一不符 ⇒ 本次无效，不得解读。

**判据 1（主判据，视觉）**：**必须自己打开 PNG 看**（CLAUDE.md 约束 1，
本项目已因转述形容词误判过一整轮），三选一：
- **无猫无桌、橙色无定形色块** ⇒ **H-inloop 成立，C 被坐实为根因**
- **清晰可辨的猫**（有虎斑/胡须/瞳孔/桌面） ⇒ **C 被否定为根因**
- 介于两者（能看出猫的轮廓但严重劣化） ⇒ C 有贡献但不足以解释全部

**判据 2（定量，与已有阶梯直接可比）**——对 `zimage_fp32_full_pipeline.png` 算
平均绝对像素差与 PSNR，落在下面这把已实测的尺子上：

| 对照 | 平均\|像素差\| | PSNR | 图像 |
|---|---|---|---|
| FP32 vs CPU 跑量化 transformer（Test B） | 9.32 | 23.89 dB | 清晰的猫 |
| FP32 vs 设备 app 真机输出 | 46.40 | 11.56 dB | 橙色色块 |
| **FP32 vs 本实验（HTP 在环）** | **?** | **?** | **?** |

- 落在 **≤ 15 / ≥ 20 dB** 一侧 ⇒ 与"CPU 量化"同类，C 被否定为根因
- 落在 **≥ 35 / ≤ 14 dB** 一侧 ⇒ 与"设备真机"同类，**C 被坐实**
- 落在中间 ⇒ 部分贡献，记为"C 有贡献但不足以解释全部"

**判据 3（一致性交叉检查）**：若判据 1 与判据 2 结论冲突（例如指标像色块但肉眼是猫），
以**判据 1（肉眼）为准**，并把冲突写进文档——本项目吃过"只看指标不看图"的亏。

## 4. 成功 / 失败的判断依据

- **成功**：出一张图 + 一组指标，按判据给出明确分支结论。
- **失败·执行方法错误**：qnn-net-run 报错、元素数不符、设备掉线。
  ⇒ 修方法重跑，判据不变，不构成对 H-inloop 的任何证据。
- **失败·方向错误**：出图与 Test B 的猫**逐像素相同** ⇒ 说明根本没走 HTP，
  必须查 `htp_run` 是否真的把设备输出接了回来。

## 5. 预算与放弃条件

- 24 次 `qnn-net-run`（8 步 × 3 段），主要成本是每次加载 1.5~2.9 GB context。
  预估 10~25 分钟。若单步超过 5 分钟，停下来查是不是每次都在重复加载。
- 若判据 1 判定"清晰的猫"⇒ **立即停止在 C 上的深挖**，回 `MAINLINE.md` 顶层重提假设。

# 🔴 结论：假设 C 被坐实为根因

**单变量对照**：与 Test B 相比，本实验只改了一件事——transformer 三段的执行后端
从「SNPE CPU 参考跑 `.dlc`」换成「设备 HTP 跑 `.bin`」。
分词、FP32 文本编码、prompt、seed(42)、调度器、VAE、步数**全部逐字节相同**。

- Test B（CPU 参考）→ **清晰的橘猫**
- 本实验（设备 HTP）→ **橙色色块，且与真机输出同类**

⇒ ②严格推论：**「HTP 执行量化 transformer 的 `.bin`」这一件事，
单独就足以把清晰的猫变成橙色色块。**

## 这同时排除了什么（重要）

本实验里，除 transformer 三段外**全部是 Python/onnxruntime 的 FP32 参考实现**。
既然它照样出色块，以下环节**全部被排除**在根因之外：

| 环节 | 状态 |
|---|---|
| C++ 实现（`PipelineZImage` 等） | ❌ 排除——本实验根本没用到 C++ |
| text encoder（含 A2 量化未验证部分） | ❌ 排除——本实验用 FP32 onnxruntime |
| VAE（A3 已否定，此处再次确认） | ❌ 排除——本实验用 FP32 onnxruntime |
| 调度器 / Euler 符号 / RNG | ❌ 排除——与 Test B 逐字节相同 |
| **量化本身** | ❌ 排除——**同一份量化模型**在 CPU 上出猫 |

⇒ **根因被压缩到唯一一点：HTP 后端对该量化 transformer 的执行。**

## 与前一轮数据的呼应

`EXP_PLAN_HTP_VS_CPU_B1B2` 实测的逐段隔离差异：
part1a **2.35%** → part1b **19.47%** → part2 **43.04%**，级联最终 **47.07%**。
且差异**逐段自生**（级联/隔离仅差 1.09 倍）、**逐位确定性**、到最终噪声预测已**弥散化**。
本实验证明：这个量级的偏差确实会毁图——
**这也反过来给"15.988% 标定点"划出了上界的另一侧**：
15.988% 无害、47% 致命，真正的阈值在两者之间（**未测定**）。
