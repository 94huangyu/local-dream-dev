### 1.1 截断在哪、有多严重

| 位置 | 内容 |
|---|---|
| `cpp/src/Config.hpp:50` | `zimage_text_max_length = 20` |
| `cpp/src/TextEncoder.hpp:214` | `min(ids.size(), 20)` —— **静默截断** |

### 1.2 20 不在模型里，是转换参数

```
text_encoder_part1..4.onnx:  IN [?, ?] → OUT [1, seq_len, 2560]      ← 完全 symbolic
Converter command: input_dim=[['add_7204','1,20,2560'], ['attention_mask','1,20']]
```

**唯一写死的是 part4 末尾四个常量**（读 initializer 得）：

```
node_slice_221 : hidden[:, 0:20, :]        val_111=0,      val_5802=20
node_slice_220 : hidden[:, 19:20, :]       val_5778=19,    val_5781=20
node_expand_74 : Expand(slice_220,[1,12,1])val_5814=[1,12,1]
node_cat_145   : Concat(slice_221, expand_74) -> caption   = [1,32,2560]
```

⇒ **32 槽 = 20 个真 token + 12 份「第 20 个 token 的复制品」**，
下游 `transformer_part1a` 的 `node_where_1` 再按 `cap_pad_mask` 把它们换成学到的 pad embedding。

## 二、Tier 1 目标与判据（**执行前定稿，不得事后修改**）

**目标**：`zimage_text_max_length` **20 → 32**，可用正文 **12 → 24 token**（翻一倍）。
**transformer 一个字节不动** ⇒ 当前 **18.67 dB 与 198 s 都不受影响**。

### 2.1 验收判据

| 编号 | 判据 | 通过 | 失败 |
|---|---|---|---|
| **T1** | 新 `caption` 输出 shape | `[1,32,2560]`，与旧完全一致 | 任何不同 ⇒ 下游契约破裂，停 |
| **T2** | 4 段新 context 的装置画像 | `dspArch=79`、`vtcmSize=8` | 不符 ⇒ 漏 `--config_file`（#95），重建 |

| **T4** | **长 prompt 生效**：13~24 token 的 prompt | 出图与截断版**不同**，且 UI 显示 `n/32` | 相同 ⇒ 截断仍在 |
| **T5** | PD / 内存 | 4 段 context 能加载，生成不被杀 | 被杀 ⇒ 回滚 |

🔴 **T3 是最重要的一条**：它证明「只是把可用长度变长」，而不是「换了一个模型」。
短 prompt 在两版里经历的计算应当完全相同（多出来的槽位本来就是 pad）。

### 2.2 机制前提（②推论，T3 就是它的检验）

Qwen 是**因果**语言模型 ⇒ 位置 20~31 的 pad token **不影响** 位置 0~19 的 hidden state。
现有实现已经依赖这一点（prompt 短于 20 时，`attention_mask` 尾部就是 0）。
⇒ 把输入从 20 槽扩到 32 槽、尾部补 pad 且 mask=0，**前 20 个位置的输出应逐位不变**。

## 七、🔴 §1.3「Tier 2 硬件不可行」已被推翻（2026-08-27，用户质疑后复查）

> 🚫 **原文保留在 §1.3，不删**（约束 2）。**推翻理由如下。**

**用户的质疑**：「当前的 onnx 就是在本机导出来的。」—— 这是**存在性证明**，我无法反驳。

### 7.1 我错在哪（三条，全部实测）

| 我的论证 | 事实 |
|---|---|
| 「权重 24.6 GB > 整机内存 23.7 GB ⇒ 导不出来」 | ①`transformer_part1.onnx` 的 `producer = pytorch 2.13.0+cpu`，**就是本机导的**，分两半（2140 / 1724 节点） |
| 只看了**物理内存** | ①宿主**提交上限 101.7 GB**（RAM 23.7 + 页面文件），fp32 也能载入（慢） |
| 默认必须 fp32 载入 | ①权重是 **F32 22.9 GB**，按 bf16 载入只要约 **11.5 GB**，本就装得下 |

⇒ **正确表述：Tier 2 是「工程量 + 精度风险」问题，不是「硬件不可行」。**
这是一次典型的**过度声称**（约束 2）：把「我没想到怎么做」写成了「做不到」。

### 7.2 而且可能有更省的路（③未验证，但值得先查）

实测 transformer 四段的 seq 相关常量**同样是少量小整数常量**：

| 段 | 含 32 | 含 4096 | 含 4128 |
|---|---|---|---|
| part1a | 5 个（如 `(1,32,3840)`、`(1,32,30,128)`） | 5 个 | 5 个 |
| part1b / 2a / 2b | 无 | 无 | 各 5 个 |

🟢 **关键：注意力头数是 30，不是 32** ⇒ **`32` 在 transformer 里无歧义**
（不像 TE 那里 32 与头数撞值，需要逐元素规则）。
且 `4128 = 4096 + 32`，`4096`（图像 token 数）保持不变。

⇒ 若可行，改法与 Tier 1 同构：`32 → L`、`4128 → 4096 + L`，**不重导**。
**不重导 ⇒ 张量名不变 ⇒ §29.8 的 Clip+FP16 白名单（值 +6.74 dB）仍然适用** —— 这是最大的好处。

### 7.3 ③ 必须先验证的（**不得据此排期**）

1. 所有 `32` / `4128` 是否**都是形状常量**？有没有 Constant 节点或非形状用途？
2. 有没有**依赖 seq 长度的 baked 数据张量**（RoPE 频率表、掩码等）？part1a 输出
   `unified_freqs [1,4128,64,2]` 是图内算的，但需确认没有 4128 长的常量表。
3. 改完后**量化 + 建 context 能否通过**（transformer 段远大于 TE）。
4. 校准数据需在新 seq 下重新生成。
5. encoding 是否仍然有效 —— caption token 恰是量级最大的那部分（HANDOVER 1273）。

**成本对比（诚实版）**：TE 段量化实测约 20 秒/段；**transformer 段是数小时/段**，
4 段量化 + 4 段建 context 是这条路的真实开销，加上磁盘（现剩 89 GB，#62 曾涨到 134 GB）。

| `val_520` | `[32,1]` | **1,2,…,32**（等差） |
| `unsqueeze_3` | `[4096,1]` | 全 False（4096 本就不变） |

⇒ **没有任何按位置学到的参数**，扩到 L 只需放大 0 张量 + `val_520` 改成 `1..L`。

### 9.3 🔴 歧义已排除（按约束 8，逐个追消费者而非假设）

`32×128 = 4096`，而 **4096 同时是图像 token 数** —— 同一字面量两种含义，是 TE 那次
（32 撞注意力头数）的同类陷阱。**逐个追消费者后确认**：所有 `4096` 都出现在**序列位**
（`(4096,64)`、`(-1,4096,128)`、`(1,4096,30,128)`、`(1,30,128,4096)`、`(4096,3)`、`(1,4096,3840)`），
**全部属于图像 token 流，必须保持不变**。`32` 同理全在序列位，且头数是 **30** ⇒ 无歧义。

**由此定稿的替换规则**：`32 → L`；`4128 → 4096 + L`；**`4096` 一律不动**。

### 9.4 ③ 仍未验证（**不得据此排期**）

1. 新 L 下**转换能否通过**（TE 那次就是转换才暴露出漏掉的常量）—— 探针成本：分钟级
2. **校准数据要在新 L 下重新生成**（transformer 的校准输入是 4128 长）—— 宿主数小时
3. **量化 + 建 context**：transformer 段是**数小时/段 × 4 段 × 2 步**，这是真正的账单
4. PD 红线：`unified` 变长 ⇒ context 涨约 1%（part2a 1887 MB，L=128 时约 1930 MB，红线 3506 MB，**余量充足**）
5. 画质需重验：encoding 会随新校准漂移，**+6.74 dB 的配方虽然名字对得上，落点是否相同未知**

### 9.5 速度代价（算出来的）

`unified = 4096 + L`：L=64 → +0.78%｜L=77 → +1.09%｜L=128 → +2.3%。
按当前 198 s 计，**约 +2~5 秒**。⇒ **速度不是障碍。**

## 十、🔴 T3 判据本身是错的（2026-08-27 验收后复查，用户要求「是不是失败也必须审查」）

### 10.1 判据的操作化先验证了 —— 这次没问题

`一条蓝色的鱼` 用真实 tokenizer 实测 = **12 token（4 正文 + 8 模板）**，
**新旧两版都未截断** ⇒ T3 确实是在比「同一输入下新旧量化的输出」，比较本身成立。
（T4 那句 = 29 token，旧版丢 9 个、新版完整 ⇒ T4 前提也成立。）

### 10.2 实测结果

| 判据 | 结果 |
|---|---|
| **T3** 出图逐字节相同 | 🔴 **不同**：PSNR 18.32 dB，99.98% 像素不同 |
| **T4** 长 prompt 生效 | ✅ **通过**：29 token 完整生效，图上出现「红色露肩毛衣」（旧版第 20 token 之后被丢的部分）|
| **T5** 内存/不被杀 | ✅ 两次生成正常完成，耗时 3m21s / 3m18s（与 #132 的 198 s 一致）|
| **#126 回归** | ✅ 两次各只写 **1 行**历史 |

### 10.3 归因（**全部实测，无推测**）

**第一步：把「图的数学」与「量化」分开** —— `scripts/te_s32_fp32_probe.py`
在 FP32 ONNX 上跑同一 prompt：

```
旧图 seq=20 输出 (1,20,2560)   新图 seq=32 输出 (1,32,2560)
前 12 个位置（真实 token）逐位相同: True
pad 区 [12:20) 最大差: 0
```

⇒ ①**图层面完全无差异，我的「因果性 ⇒ 前面位置不受影响」前提在 FP32 下成立**。

**第二步：差异来自量化** —— 用 `snpe-dlc-info -d -s` 导出两版 part1 的全部 encoding 比对：

- **753 个 encoding 里 487 个不同**
- 量程相对变化：**中位数 0.0251%**、p90 0.58%、p99 7.85%；>1% 的只有 66 个
- 🔴 **变化最大的四个全是位置索引张量**（`transpose` / `matmul` / `cat` / `_to_copy_1`），
  量程 **19 → 31**（+63.16%）

### 10.4 🔴 结论：T3 要求的是**结构上不可能满足**的事

位置索引张量的取值范围**就是 `0..seq-1`**，把 seq 从 20 改成 32，它的量程必然从 19 变成 31。
⇒ encoding 必然变 ⇒ caption 必然变 ⇒ 出图必然变。
**任何校准技巧都消不掉这一条。**

我先前说「encoding 逐位相同」只对**契约里可见的那 4 个张量**成立
（靠「复制最后一行」保住了它们的量程），**内部 749 个张量我根本没比对过**就下了结论
—— 这是**超出证据范围的表述**（约束 2）。

🚫 **更根本的问题：T3 违反了本项目自己写下的原则。**
`MAINLINE §2.1.1` 明写：

> 「两个量化配置彼此差异大是必然的，**不构成「无用功」的证据** —— 基准是 FP32 参考，
> 不是上一个量化版本。同 prompt 同 seed 下两个量化版本出完全不同的图，**是预期之内的**」

**我设计 T3 时拿「上一个量化版本」当基准，正是这条明令禁止的做法。**

### 10.5 因此的正确判读

- **T3 失败 ≠ 交付有缺陷。** 它测的是一件不该要求的事。
- **已排除缺陷的证据**：FP32 图层面逐位相同；encoding 变化量级与任何一次重量化无异
  （中位数 0.025%）；两次生成正常、耗时不变、历史行数正确。
- **仍未回答的问题**：32 槽版相对 **FP32 参考**是更近还是更远？
  ⚠️ **只能在研究流水线里做**（app 没有 FP32 参考，见 #130），需要为同一 prompt
  生成 FP32 参考再比 L3 PSNR。**在做这件事之前，不得声称画质更好或更差。**
