# EXP_PLAN_ODLBC_SPEED —— §6 的 B：`O` / `dlbc` 对**速度**的影响（廉价筛查先行）

**定稿**：2026-08-29　**判据事前锁定，不得事后修改（约束 4）**
**与 `EXP_PLAN_O_DLBC.md` 的区别**：那份测的是**算子级精度**（单算子探针 `fc99`），
本份测的是**生产段的计算速度**。**两份不得互相引用结论。**

---

## 一、为什么现在能做，以及一处措辞订正

- **前置已具备**：测速协议已标定（#144，`\|B2−B3\|/mean = 0.152%`）⇒ 个位数 % 的效应现在测得出来。
- 🔴 **订正 §6 的 B 行**：它写「#94 已实测四臂逐位相同 = **零精度风险**」。
  #94 的原文是「对**算子级**精度无影响」，试验台是单算子探针 `fc99_fp32`。
  **从单算子外推到全模型超出证据范围**（约束 2）⇒ 本实验**必须自带精度判据**（G3）。
- ①**实测（本轮，宿主）**：部署四段的 `--config_file` detail **只有 `devices` 段、没有 `graphs` 段**
  ⇒ 按 #93，`O`/`dlbc` 在现网产物里**从未生效过**（是默认档）⇒ 这条确实没测过。

## 二、目标与预期

**目标**：判断 `O` / `dlbc` 是否值得为之付「3 臂 × 4 段 ≈ 3 小时建图 + 设备实测」。

**预期**：③**无实证依据**。`O` 是官方定位的性能选项（#19 机制性结论），
但 #19 同时实测「O=3 只让体积变大」，②对速度是正是负**没有任何数据**。

## 三、两阶段，先筛后全

### 阶段 1：廉价筛查（**只建 part1b 一段**，宿主 ~30~60 分钟 + 设备 ~10 分钟）

| 臂 | `graphs[0]` |
|---|---|
| **CTRL** | `{graph_names:[part1b_fp16_L80_fp32], vtcm_mb:8}`（`vtcm_mb` 对本图无效果，#93 实测） |
| **O3** | CTRL + `O:3` |
| **DLBC** | CTRL + `dlbc:1` |

**为什么拿 part1b 做筛查**：它在步循环内**常驻且每步都算**，是纯计算段（不含每步加载），
信噪比最高；且它的量化 DLC 已在盘（`part1b_fp16_L80_quantized.dlc`），不必重量化。

**测速方法**：`scripts/speed_split.py` 的斜率截距法（`--num_inferences 1 vs 5`），
**取斜率 = 纯计算时间**，避开 #132 踩过的分母陷阱（`qnn-net-run` 要写盘，截距不可当计算）。

⚠️ **措辞纪律**：这是 `qnn-net-run` **离线单段计时**，
**不得**直接等同于 app 内每步耗时（#132 已因此栽过一次）。它只用于**臂间相对比较**。

### 阶段 2：全量（**仅当阶段 1 通过**）

四段全建 + 真实 app 走 #144 的冷机协议。**阶段 1 不过就不做**，省约 3 小时。

#### 🔴 阶段 2 判据补充（2026-08-30 事前锁定，在阶段 2 执行之前写）

**新增前提**：阶段 1 定稿时 F（四段全常驻）还没交付。现在 F 已交付，
ION 峰值 **9100 MiB**、峰值时余 **839 MiB**。而 O3 让 context **+2.34%**
⇒ 预计 ION 增加约 **+203 MiB** ⇒ 余量可能降到约 **640 MiB**。
**两个优化叠加的内存代价必须先测，不得沿用 F 的实测值。**

**执行顺序改为「先内存门，后交付」**：

| 步 | 动作 | 成本 |
|---|---|---|
| **2a** | 推四段 O3 bin，用 `quadctx_probe` 测四段共驻 ION（**不改契约、不装 APK、不碰现网**） | 设备 ~15 分钟 |
| 2b | 仅当 2a 通过：重生契约（`sha256`/`size_bytes`/`exact_bytes` 三样都要，#134 栽过）→ 宿主 `contract_dryrun.py` → 下发 → 冷机测速 | 设备 ~20 分钟 |

#### G5　内存（阶段 2 专用，**先于一切交付**）

```
四段 O3 全部 createFromBinary 成功，且峰值时 MemAvailable ≥ 600 MiB  ⇒ 🟢 继续 2b
四段成功但 MemAvailable < 600 MiB                                    ⇒ 🟡 余量不足，**不交付**
任一段失败                                                            ⇒ ❌ O3 与 F 不可兼得
```

**600 MiB 这条线的来源**：F 单独交付时实测峰值余 **839 MiB** 且连续 3 张稳定；
O3 预计吃掉约 203 MiB ⇒ 839 − 203 = 636 MiB。取 600 作为「不比现状差太多」的下限。
⚠️ ③该阈值**没有实测依据说明 600 MiB 就安全**，它只是「相对现状的退化幅度可接受」的约定。

#### G6　若 O3 与 F 不可兼得 —— **事前定好取谁**

```
F 已实测 −21.2%（43.4 秒）；O3 段级 −9%，端到端③未测，粗估 −5~7%（10~14 秒）
⇒ **保 F，弃 O3**。
```

🔴 **这条必须事前写死**，否则拿到数据后容易被「都想要」带着走。
O3 不是白建：产物留档，将来若 context 变小（换量化配置/换模型）可重新评估。

## 四、判据（🔴 事前锁定）

### V0　生效门（先决条件）

```
md5(O3) ≠ md5(CTRL)  且  md5(DLBC) ≠ md5(CTRL)
```
相同 ⇒ 该臂**选项未生效**（多半是 `graph_names` 填错，#93：填错不报错、整段落空），
该臂退出判定，**不得记为「无效果」**——那是执行错，不是方向错。

### G-screen　阶段 1 主判据

以 CTRL 的斜率 `S_CTRL` 为基准：

```
某臂 S ≤ 0.95 × S_CTRL   ⇒ 🟢 有速度收益，进入阶段 2
某臂 S ≥ 1.05 × S_CTRL   ⇒ ⚠️ 有害，记录并确保产品配置不开
全部落在 0.95~1.05        ⇒ ❌ B 关闭，不做阶段 2（省约 3 小时）
```

**5% 这条线的来源**：part1b 计算约占每步 14 s / 25.5 s ≈ 55%；
段级 5% ⇒ 端到端约 2.7%，而尺子精度是 0.152% ⇒ 仍有约 18 倍余量可判。
低于 5% 的段级收益，端到端不值得为它付 3 小时 + 一次交付风险。

### G3　精度（阶段 2 才有，**bug 判据不是权衡项**）

```
出图 sha256 == 基线 5ce17d9a7d1372055666b0b54cf46b8c59b5d7fdb01bda4b1721f38224a3a21c
```
不同 ⇒ ❌ 查清再谈速度。**不许**退而用「三层指标在噪声内」放行。

### G4　体积 / PD

任一臂建图报 `available PD` ⇒ 该臂否决（#57 红线）。
体积显著变大（#19 实测 O=3 会变大）⇒ 记录，并在阶段 2 前重算 #145 的内存账
（**context 变大会直接恶化 #146 的可行性**）。
