## 一、为什么现在做，以及它能改变什么

**必须先答"这对顶层问题有什么贡献"（约束 6），否则就是漂移。**

至今所有算子级工作都在 **part1b 的 `linear_99`** 上（自审第 2 条已多次记录：
"修最方便测的而非最该修的"）。而 §3.2 实测：part2 基线 **41.24%**、per-row **28.52%**，
上游两段全部改善只贡献约 **2.17 pp** ⇒ **剩下约 41 pp 是 part2 自己的**。

**它能改变什么**：
- 若 part2 的误差增长机制**与 part1b 相同**（沿链累积 + RmsNorm 固有放大，#97）
  ⇒ #98 成立、无新杠杆 ⇒ **"A16W8 在 v79 上就这样了"这个结论基本坐实**，可据此收口。
- 若 part2 有**不同的**机制（某个算子被明显做坏）⇒ **新目标**。

⇒ **这是新杠杆最后可能藏身的地方。** 无论哪个结果都是可交付的。

## 二、🔴 装置的关键发现（今日实测，省掉 6 小时）

原以为"取中间张量必须把 tap 焊进 ONNX 重新量化建图"（MAINLINE §7.3）。**实测订正**：

```
ERROR: --set_output_tensors can only be used with graph prepared online
       using the option --model or --dlc_path
```

⇒ 限制不是"图已 finalize"，而是**要求在线建图**。
⇒ **不必焊 tap、不必重量化**：把现有 `part2a_fixed_perrow.dlc` / `part2b_fixed_perrow.dlc`
推到设备，用 `--dlc_path` 在线建图 + `--set_output_tensors` 即可（part1b 的 fc_probe 正是这么做的）。

### ⚠️ 但有一个已知会压死手机的坑（#55 / 约束 9 自审第 7 条）

part2 设备端在线建图**曾经把整机压死**（RSS 5.76 GB，15.4 GB 手机只剩 115 MB）。
2026-08-22 实测手机可用内存仅 **1653 MB / 15107 MB**。

🔴 **前置条件（不满足不得开始）**：
1. **用户在场**（不得在人不在时做有卡死风险的设备操作）
2. 开跑前先清内存或重启手机，`free -m` 的 free ≥ **6000 MB**
3. 一次只跑 **part2a 或 part2b 之一**，不得同时

## 三、实现路径

**口径选择：段内隔离（喂 FP32 输入），不是在环。**
理由：在环时 part2 的输入 `unified` 已带 78.77% 主体误差、主体余弦 0.7986（今日实测），
误差起点不为零，无法把"part2 自己产生的"与"上游带进来的"分开。
§3.2 的 41.24% / 28.52% 基线正是隔离口径 ⇒ **与之可比**。

1. ~~**宿主侧 CPU 参考**：`snpe_runner.py` 跑同一份 DLC~~
   🔴 **2026-08-22 执行中作废并改道（明写，判据结构不变）**：
   `snpe-net-run` 拒绝执行 per-row DLC ——
   `error_code=202; Invalid fixed point parameter. **Dequantization of axis-quant tensor
   is not supported for FullyConnected**`
   ⇒ **SNPE CPU 运行时不支持 per-axis 权重的反量化**，跑不了部署用的 per-row DLC。
   （顺带澄清：part1b 的 `fc_probe` CPU 参考用的是 `dlc_pipeline` 下的**基线 per-tensor** DLC，
   不是 per-row ⇒ **历史上所有「CPU 参考」必然都是 per-tensor 配置下的**。）

   **改用**：直接用 **FP32 ONNX（`transformer_part2a_fixed.onnx`）+ onnxruntime** 算出同名张量作为**真值**。
   这比"浮点执行量化 DLC"更干净（不含任何量化，也绕开 #35 的浮点/定点前提问题），
   且给出的是**相对真值的绝对误差**，正是归因需要的量。
   ⚠️ **参照系变了必须记在结论里**：`cos(X)` 现在是「HTP vs FP32 真值」，
   不是「HTP vs CPU 参考」⇒ 它包含量化误差本身，不只是 HTP 特有误差。
   判据（按算子类型聚合 `Δcos`）**结构不变**。
2. **设备侧 HTP**：`qnn-net-run --dlc_path <part2a> --set_output_tensors <名单>`
3. 探针名单沿**真实依赖链**取（`trace_dag.py`，**不是 Id 顺序**——#24 已固化为约束 8：
   Id 顺序 ≠ 依赖顺序）

## 四、🔒 判据（事前锁定）

**度量**（约束 7）：主体相对 L2（`|a| ≤ p99`）+ 主体余弦 + 前 1% 能量占比。
🔴 **余弦 < 0.9 的张量退出定量比较**（#97 的教训：在已毁区域做定位无意义；
约束 7 的硬线是 0.3，本实验取更严的 0.9 以保证"误差仍可比"）。

**主判据**：对链上每个算子 X 计算 `Δcos(X) = max(cos(输入)) − cos(输出)`，按**算子类型**聚合。

| 结果 | 判定 | 后续 |
|---|---|---|
| RmsNorm 的 `Δcos` 总和 ≥ 2 × 其余类型合计，且 FC 放大 ≈ ×1.0 | ✅ **与 part1b 同机制** | #98 成立，**无新杠杆** ⇒ 收口 |
| 某个**非 RmsNorm** 算子类型的 `Δcos` 总和 ≥ 2 × RmsNorm | 🟢 **新目标** | 按该算子展开 |
| 两者相当 | 🔶 部分 | 报告比例，不得宣称任一方 |

**并行**：对判定为"放大点"的 RmsNorm，用 `rmsnorm_amp_probe_v2.py` 的同一套装置
（float64 精确复现 + **DLC 量化 gamma**）算 `A_float`，检验 `A_htp/A_float ≤ 1.3`
⇒ 若成立则与 #97 同结论（固有，非 HTP 缺陷）。

### V 门
- **V0 装置门**：探针集合必须构成**连通的依赖链**；Reshape 视为透明
- **V1 有效性门**：两侧元素数一致；输出字节数正确（防静默缩批，约束 3）
- **V2 可比性门**：参与比较的张量主体余弦 **> 0.9**，否则退出
- **V3 复现门**（仅 RmsNorm 那一步）：float64 复现 vs 真实 CPU 输出相对差 < 1%，
  🔴 **必须用 DLC 里的量化 gamma，不是 ONNX 的 fp32 gamma**（§15.30 教训，第一版就栽在这）

## 五、失败归因

- V2 大面积不过（余弦 < 0.9）⇒ part2 内部误差增长太快，**探针要往上游加密**，不是结论
- V3 不过 ⇒ 复现不对（gamma/eps/轴），修正后重跑，判据不变
- 设备卡死 ⇒ **执行方法错误**，先满足 §二 的三条前置条件
