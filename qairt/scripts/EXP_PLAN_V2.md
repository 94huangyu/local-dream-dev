# 实验方案 V2（作废 EXP1_PLAN.md，执行前定稿）

## 0. 为什么作废 V1

V1 的前提是"设备画质发闷、需要提高精度"。**这个前提是错的**——我自己看图确认：

| | 图像内容 |
|---|---|
| **FP32**（`zimage_fp32_full_pipeline.png`） | 照片级橘猫端坐木桌上，毛发/虎斑/瞳孔/木纹全部清晰，背景有虚化画框和绿植。**完全符合 prompt** |
| **设备量化**（`sm8750_test2.png`） | 橙色无定形色块，**没有猫、没有桌子、没有任何可辨识形状**，另有明显横向条带伪影 |

失败类别不是"精度不够导致质感差"，而是 **语义/形状完全没有生成出来**。
文档里"能看出蓬松的猫状轮廓"是过度乐观的描述，不应继承（这是本会话第二次栽在
"继承文档里未经自己验证的描述"上，第一次是 `add_54` 被标成"第1层"）。

## 1. 被忽略的重大混淆变量

FP32 那张图由 **Python 脚本** `zimage_fp32_pipeline.py` 产生；
设备那张图由 **C++ 实现** `PipelineZImage.hpp` 产生。**这是两套不同的实现。**

所以"FP32 好 / 设备坏"这个对比里同时变化了**两个**因素：

1. 量化 vs 不量化
2. C++ 实现 vs Python 实现

而且已知这条链路上**确实出过实现性 bug**：`cap_pad_mask` 极性反了、Euler step 符号反了——
两个都是 C++ 侧的 bug。没有任何证据排除还存在第三个、第四个。

**13.9～13.17 全部的量化误差定位工作，都建立在"差异 = 量化"这个未经验证的前提上。**

## 2. 候选原因（互不排斥）

| 编号 | 候选原因 | 现有证据 | 是否被验证过 |
|---|---|---|---|
| C1 | transformer 量化误差 | `add_138` 相对误差 26.9%（实测） | 误差已量化，但**与画质的因果关系未验证** |
| C2 | text encoder 量化误差 → caption 条件被破坏 | 当年做过余弦相似度验证 | 验证过，但是在旧交付上；且"隐藏层选择"一直标注未验证 |
| C3 | VAE 量化误差 | 第三节诊断实验称 VAE 路径正常 | 结构性验证，非数值精度验证 |
| C4 | C++ 实现仍有未发现的 bug | 已发现并修复过 2 个同类 bug | **完全未排查** |

## 3. Test A：text encoder 量化对 caption 条件的影响（先做，成本低）

**目标**：确认量化后的 caption 嵌入是否仍然携带正确的语义条件。

**路径**：用同一组 `input_ids`/`attention_mask`（取自 Python 脚本的分词结果），
- FP32 侧：onnxruntime 跑 `text_encoder_part1~4` → `caption_fp32`
- 量化侧：`snpe-net-run` 跑四个 `text_encoder_part*_quantized.dlc` → `caption_quant`

**指标**：逐 token 余弦相似度、相对误差、以及最关键的——把 `caption_quant` 喂进
**FP32 transformer + FP32 VAE** 出一张图。

**预期结果（执行前登记）**：我预测余弦相似度 > 0.99，出图仍是可辨识的猫。
理由：当年做过余弦相似度验证且通过。

**验收标准**：
| 结果 | 判读 | 后续 |
|---|---|---|
| 出图仍是清晰的猫 | C2 被排除 | 进 Test B |
| 出图变成色块 | **C2 就是根因** | 停止 transformer 量化工作，全力查 text encoder |
| 出图介于两者之间 | C2 有贡献但非唯一 | 记录贡献度，仍需 Test B |

**成本**：4 次 snpe（text encoder 分段较小，约 8 分钟）+ 1 次 FP32 transformer+VAE（约 10 分钟）≈ 20 分钟。

## 4. Test B：transformer 量化对成图的影响（决定性实验）

**目标**：在**排除实现差异**的前提下，单独测量 transformer 量化对最终图像的影响。

**路径**：用**同一个 Python 脚本、同一 prompt、同一 seed(42)**，只把去噪循环里的
`part1a/1b/2` 从 onnxruntime 换成 `snpe-net-run` 跑量化 DLC，其余全部保持 FP32
（text encoder、调度器、VAE 都不变）。

```
文本编码(FP32) → [8步: part1a(量化) → part1b(量化) → part2(量化) → 调度器(FP32)] → VAE(FP32) → PNG
```

**这是唯一能把"量化"和"C++实现"分离开的实验。**

**预期结果（执行前登记）**：我预测**出图会明显劣化但仍保留猫的大致形状**。
理由：`add_138` 26.9% 的相对误差不小，但下游有多处归一化（实测见过 168→0.18 的衰减）。
**我明确承认另两种结果同样可能**，且每种都有明确含义（见验收标准）。

**验收标准（执行前定稿，不得事后调整）**：
| 结果 | 判读 | 后续 |
|---|---|---|
| **出图 ≈ 清晰的猫**（与 FP32 基准接近） | **C1 被否定**：transformer 量化不是根因 | 全力转查 C4（C++ 实现），13.9～13.17 的定位工作虽正确但与画质无因果关系 |
| **出图 ≈ 橙色色块**（与设备输出接近） | **C1 被确认**：transformer 量化足以造成该失败 | 量化优化方向成立，回到 13.17 的机制去设计修复 |
| 出图介于两者之间 | C1 有贡献但不足以解释全部 | C1 与 C4 并存，两条线都要查 |

**必须通过的有效性检查（任一不通过则结果作废）**：
| 检查 | 判据 |
|---|---|
| V1 dtype/shape | 每个中间 `.raw` 字节数 = shape连乘 × dtype字节数，逐个核对（`unified_mask` 是 bool、`latents_shape` 是整型） |
| V2 量化侧复现性 | 第 0 步的 `add_138` 误差 ≈ 321.8（8.4 节值），偏差 < 5% |
| V3 FP32 基准可复现 | 用同一脚本、同一 seed 重跑纯 FP32，应得到与 `zimage_fp32_full_pipeline.png` 一致的图 |

**成本**：8 步 × 3 次 snpe = 24 次调用，每次约 4 分钟（模型加载占大头，且步间有依赖无法批量）
≈ 100 分钟。加文本编码和 VAE 约 110 分钟。

## 5. 失败分析预案（区分方向错 vs 执行错）

| 现象 | 更可能是 | 排查动作 |
|---|---|---|
| 中间出现 NaN/Inf，或图全黑/全白 | 执行错 | 段间 dtype/shape 喂错，回到 V1 |
| V2 不通过 | 执行错 | 输入字节或模型选错 |
| V3 不通过（FP32 重跑对不上原图） | 执行错 | seed/prompt/脚本版本不一致，先对齐再谈量化 |
| V1~V3 全过，Test B 出清晰的猫 | **方向错** | C1 被否定。这意味着本会话 13.9～13.17 的全部工作虽然结论正确，但打错了目标 |
| V1~V3 全过，Test B 出色块 | 方向正确 | 回到 13.17 设计修复 |

## 6. 执行顺序与理由

**Test A → Test B**。
理由：Test A 成本只有 Test B 的 1/5，且它检验的 C2 在链路上更靠前——若 caption 条件本身
就被破坏，后面所有 transformer 层面的分析都无意义。先做便宜且更靠前的。

**在 Test A、Test B 都完成前，不设计任何修复方案。**
