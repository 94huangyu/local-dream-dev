# EXP_PLAN_SYM_FC_OVR —— 只把 FullyConnected 的权重改成对称量化，能否消掉 HTP 的偏差？

定稿时间：2026-08-15（**执行前定稿，判据不得事后修改**）
台账归属：**#7（选择性对称权重 FC-only）**，机制依据 **#40**，闸门 **#45**
前置实验：`EXP_PLAN_SYM_WEIGHTS`（全局 symmetric ⇒ RmsNorm 编不出图，H-sym 未被验证也未被否定）
主线贡献：顶层问题「如何解决 HTP 的数值问题」——这是**第一个有三条独立证据支持的可修方案**

---

## 0. 假设与它的证据基础

**H-sym-FC**：A16W8 下 **FullyConnected 权重的非对称量化**（z_w ≠ 0）在 HTP(v79) 上
导致系统性精度损失；把这 59 个权重改成对称（z_w = 0）后，HTP 的偏差显著减小。

**机制**（审查者 §3.8 + 台账 #40，①实测）：非对称权重的定点 MatMul 展开为
`acc = Σ q_x·q_w − z_w·Σ q_x − …`。实测 **offset 项/主项 = 0.891~0.979**，
两个几乎等大的数相减 ⇒ 灾难性抵消，中间精度稍有不足即吃掉有效位。
对称量化令 `z_w = 0`，该项**整体消失**。

**其余支持证据**：
- 官方**通用最佳实践**（适用范围已核对，非 A16W16 专属）：
  "It is **recommended** to always use symmetrical quantization of weights ... to obtain
  best accuracy on HTP based targets."（`htp_backend.html`，best-practices 节）
- ①实测：part1b 的 59 个 FC 权重**全部非对称**（offset −60 ~ −132，理想对称为 −128）
- ①实测：HTP 主体口径与 FP32 真值的余弦仅 **0.6033**，而 CPU 参考是 **0.9975**

> ⚠️ 以上只说明"违反了建议 + 存在可致害的机制"，**不能证明它就是根因**。
> 本实验补的正是这个因果证据。在拿到结果前，H-sym-FC 只是假设。

## 0.1 【先决条件 · 已完成】OpDef 支持性（约束 5，2 分钟查表 vs 1~2 小时试错）

`scripts/check_opdef_support.py`，依据 `docs/QAIRT-Docs/QNN/OpDef/HtpOpDefSupplement.html`：

| 算子 | UFxp16 激活下 in[1] 允许的类型 | **SFxp8 支持?** |
|---|---|---|
| **FullyConnected** | SFxp16 / **SFxp8** / UFxp16 / UFxp8 | ✅ **是**（`UFxp16 / SFxp8 / SFxp32 / UFxp16` 在表内） |
| MatMul | SFxp16 / **SFxp8** / UFxp16 / UFxp8 | ✅ 是 |
| **RmsNorm** | SFxp16 / UFxp16 / UFxp8 | ❌ **否** ← 上一轮全局 symmetric 失败的原因 |

⇒ **只点名 FC、不点名 RmsNorm，在 OpDef 层面是合法的。**（这是本方案与上一轮的唯一差别）

## 1. 实现目标（单变量）

产出一份 part1b 量化 DLC，与基线 `transformer_part1b_quantized.dlc` **只有一处不同**：
59 个 FullyConnected 的权重张量用**对称** encoding（sFxp_8, z_w=0），
其余（44 个 RmsNorm 的 gamma、全部激活、全部 bias）**保持基线不变**。

## 2. 实现路径

### 2.1 对称 encoding 的来源（**不自己推公式**）

直接**复用 SDK 自己算出来的对称 encoding**：上一轮 `--param_quantizer_schema symmetric`
产出的 `symw/transformer_part1b_symw_quantized.dlc` 里，这 59 个张量已经是
`sFxp_8 / offset=0 / min=−128s / max=127s`。把它们的 `scale` 原样搬进 overrides JSON。

> 这样做的理由（约束 8）：量化器的对称 min/max 取法不是简单的 `max|w|/127`
> （实测 `val_1788` 的 SDK 值 0.020669290796 ≠ max|w|/127 的估算值），
> **与其猜公式，不如直接用 SDK 自己的输出**。零猜测。

### 2.2 名字映射（**#45 的静默失效陷阱**）

overrides 必须用 **ONNX 张量名**：
- `val_1788` 类（MatMul 的 B）：DLC 名 == ONNX 名，直接用
- `layers.8.adaLN_modulation.0.weight_permute` 类（Gemm 的 B）：**去掉 `_permute` 后缀**
- 每个名字都要在 `transformer_part1b.onnx` 的 initializer 集合里**验在**，验不到就报错退出

### 2.3 三步命令

```
① qairt-converter  --quantization_overrides sym_fc.json --float_bitwidth 32   (~60 s)
② qairt-quantizer  （与基线逐项相同的参数，见 2.4）                            (~45~60 min)
③ qnn-context-binary-generator --htp_socs sm8750                              (~25 min)
④ 设备 HTP 跑，输入取 testB s0 的 part1b 输入（与实验 A 逐字节相同）           (~1 min)
⑤ 宿主 SNPE CPU 参考跑同一份新 DLC（走 scripts/snpe_runner.py，约束 3）
```

### 2.4 量化参数（从 `transformer_part1b_dlcinfo.txt` 的 Quantizer command 逐项照抄）

```
--weights_bitwidth 8 --act_bitwidth 16 --bias_bitwidth 32
--use_per_channel_quantization --act_quantizer_calibration min-max
--param_quantizer_calibration min-max --input_list <基线同一份 input_list_raw.txt>
```
（`act_quantizer_schema`/`param_quantizer_schema` 均保持默认 asymmetric —— **不动**，
对称性只通过 overrides 施加到那 59 个张量。）

## 3. 先决门（Gate）：必须先过，过不了就不投 45 分钟

### G0（已过）OpDef 支持 SFxp8 —— 见 0.1

### G1 —— overrides 生效计数
最小验证：**只点名 1 个** FC 权重（`val_1800`，即 `linear_99` 的 B）。
日志必须出现 `Processed 1 quantization encodings`（**N == 点名数**）。
- N == 0 ⇒ 名字错了（静默失效），修名字重来，判据不变
- N != 点名数 ⇒ 部分未匹配，必须查清后才能继续

### G2 —— 转换产物的浮点位宽没被偷换（**本轮新发现的陷阱**）
①实测：上一轮 `ovr/part1b_ovr.dlc` 的张量**全部是 Float_16**（1607 个 Float_16、0 个 Float_32），
而基线 fp32 DLC 是 Float_32。官方文档 `converters.html`：
"**Float bitwidth 16 is the default bitwidth for source model with quantization encodings or overrides**"。
⇒ 不显式给 `--float_bitwidth 32`，overrides 会顺带把整张图降成 FP16，**破坏单变量**。

G2 判据：新转换 DLC 的浮点张量必须仍是 **Float_32**。
- 若显式 `--float_bitwidth 32` 仍得到 Float_16 ⇒ 该混淆无法消除，
  则**必须**在步骤 ③ 之后补做 G4 的 encoding 比对来证明混淆无影响，否则结论不成立。

### G3 —— 类型确实变了、且只变了该变的
量化后的新 DLC 必须满足**全部三条**（`scripts/check_sym_fc.py` 自动核）：
1. 59 个 FC 权重：`sFxp_8` 且 `offset == 0`（约束 8：**有符号表示下对称是 offset==0，不是 −128**）
2. 44 个 RmsNorm 的 gamma：**与基线逐字段相同**（未被牵连）

   > ⚠️ **【判据操作化订正 #2，2026-08-15 20:20，设备实测产生之前】**
   > 原写法是"仍是 `uFxp_8` 且 **`offset != 0`**"。实测发现**基线自身**就有 **14 个** gamma
   > 是 `offset == 0`（`layers.*.attention.norm_q/norm_k.weight`，值域 `[0.0, 2.015625]`
   > 全为正 ⇒ 非对称 min-max 天然落在 offset 0）。
   > ⇒ 原写法会把"与基线**完全一致**"这一最理想状态误判为不合格。
   > 这是约束 8 表格第一行（"对称 ⇔ offset == −128"）的同类错误：
   > **把某个具体数值编码当成语义判据**。
   > 改为直接与基线逐字段比对，**严格更强**（相同 ⇒ 必然未被牵连）。
   > 实测结果：**44/44 与基线逐字段相同**。
3. 59 个 FC 的 bias 仍是 `sFxp_32`

任一条不满足 ⇒ 本次无效，不得解读，回到执行方法层修。

### G4 —— 上游未被扰动（排除"改的不止是权重"）

> ⚠️ **【结果产生前的判据修正，2026-08-15 19:30；理由与证据如下，非事后放宽】**
> G4 原写法是"**全部激活** encoding 的 scale 相对差 > 1% 的张量数必须为 0"。
> 定稿后按约束 8 用**已知样本**（`symw` 全局对称 DLC，一次合法的纯权重改动）预跑该判据：
> **42 个激活张量的 scale 漂移超过 1%，最大 6.98%**（`mul_484` 7.506e-3 → 8.030e-3）。
> ⇒ 该写法**必然把合法结果判成无效**：权重变了 ⇒ 校准推理算出的激活值变了 ⇒
> min-max 校准出的激活 encoding 本来就会跟着变。**这是被测效应本身，不是混淆。**
> 原判据的目标（排除 FP16 混淆）**已被 G2 单独完成**（1607 Float_32 / 0 Float_16），G4 无需重复。
> 修正后的 G4 改测**上游**，即不可能被权重改动影响的部分。
> 已用同一已知样本验证该新写法成立（见下）。

新 G4：新 DLC 与基线 DLC 的**图输入** encoding（`add_138` / `add_131` / `tanh_19` /
`select_45` / `select_46` / `adaln_input`）必须**逐字段完全相同**。
- 已知样本验证：`symw` 全局对称 DLC 上，这 6 个输入的 encoding 与基线**逐字段相同** ⇒
  该判据不会误杀合法改动，只会抓到"校准数据/浮点路径被换掉"这类真混淆。
- 不同 ⇒ 说明改动波及上游，单变量被破坏，结论降级为"相关性"，不得称因果。

**同时记录（观测项，不作判据）**：激活 encoding 漂移 >1% 的张量个数与最大漂移。
它反映"对称权重对下游校准的影响面"，是有价值的现象，但**不用于判定成败**。

## 4. 验收标准（判据，**事后不得修改**）

### 4.1 度量口径（约束 7）

真值：`vs_fp32/unified_fp32.raw`（onnxruntime FP32，与隔离输入逐字节相同）。
①实测能量集中度：**前 1% 元素占 `||a||² ` 的 99.83%** ⇒ **全量口径不可用于描述整体**，
主判据一律用**主体口径**（`|a| ≤ p99(|a|) = 2.6547`，主体 std = 0.6235）。

统一由 `scripts/metrics_unified.py` 计算，已实测的基线（本轮重算，同一脚本同一口径）：

| 配置 | E_all | **E_bulk** | **cos_bulk** | slope_bulk | 主体 std |
|---|---|---|---|---|---|
| FP32 真值 | — | — | 1.0000 | 1.0000 | 0.6235 |
| SNPE CPU 参考 | 1.1757% | 7.0863% | **0.9975** | 1.0057 | 0.6286 |
| **设备 HTP（基线）** | 19.2406% | 114.798% | **0.6033** | 0.8622 | 0.8910 |
| 设备 HTP（O=3 对照） | 19.2448% | 114.890% | 0.6028 | 0.8618 | 0.8912 |

### 4.2 为什么主判据用**余弦**而不是误差百分比（约束 7 + 约束 8）

约束 7 明确：**误差 >100% 时张量已与真值去相关，比较两个大误差的大小没有意义**。
基线 HTP 的 `E_bulk` 已是 **114.8%**，因此**不得**用"114.8% → xx%"来判定成败。
余弦有界、单调、且不受"大误差不可比"限制，故定为主判据。

**该操作化已用两个已知样本验证（约束 8，不是拍脑袋）**：
- 已知"完全正确"样本：CPU 参考 ⇒ cos_bulk = **0.9975**
- 已知"确定无效"样本：O=3 重建（#19 已独立证明无精度影响）⇒ Δcos = **−0.0005**
⇒ 该指标的**无效变更本底约 ±0.001**，判据阈值取其 5~10 倍以上，安全。

### 4.3 主判据（cos_bulk）

记新配置的主体余弦为 `cos_sym`，`Δ = cos_sym − 0.6033`，
可弥合缺口 `G = 0.9975 − 0.6033 = 0.3942`。

| 结果 | 判定 |
|---|---|
| **Δ ≥ 0.20**（弥合 ≥ 50% 缺口） | **H-sym-FC 成立**，权重非对称是主因之一 ⇒ 推进到三段全量重量化 + 在环出图 |
| **0.05 ≤ Δ < 0.20** | **部分成立**：按 `Δ/G` 报告弥合份额，**不得**宣称"找到根因"，须继续找剩余部分 |
| **\|Δ\| < 0.005** | **H-sym-FC 被否定**（变化在无效本底 ±0.001 的 5 倍以内）⇒ 转下一条线索，**不再重复对称权重方向** |
| **Δ ≤ −0.005** | **反向恶化** ⇒ 同样否定，并记录"对称权重在 HTP 上更差"这一反直觉事实 |
| 0.005 ≤ Δ < 0.05 | 微弱改善，等同于**否定**（不足以支撑三段重量化的成本），但如实记录数值 |

### 4.4 次判据（机制，不单独定结论）

- **slope_bulk**：基线 0.8622（HTP 把幅值系统性算小 13.8%）。
  若 `slope_sym` 明显趋向 1.0（例如 ≥ 0.95），说明"系统性增益缩小"确由权重非对称造成
  —— 即使主判据只落在"部分成立"，这也是一条明确的机制结论。
- **主体 std**：基线 HTP 0.8910 vs FP32 0.6235（偏大 43%）。记录其变化方向。

### 4.5 对照判据（防止"改坏了别处"）

新 DLC 在 **SNPE CPU 参考**上跑（约束 3：走 `snpe_runner.py`）：
`cos_bulk_cpu_sym` 必须 ≥ **0.99**（基线 0.9975）。
若 CPU 侧显著变差 ⇒ 对称量化本身损失了精度，即使 HTP 侧改善也不能直接采纳，需权衡。

### 4.6 有效性自检（不过则本次无效，不得解读）

- 输出 `unified` 必须是 **15,851,520** 个 float32（63,406,080 字节）——防静默缩批（约束 3）
- 设备输入必须与实验 A 的 `testB/s0_transformer_part1b/*.raw` **逐字节相同**（md5 核对）
- 新旧量化 DLC 的 md5 必须**不同**（相同 ⇒ 参数没生效）

## 5. 成功 / 失败判断

- **成功**：拿到 `cos_sym`、`slope_sym`、`cos_bulk_cpu_sym`，按 4.3 给出明确分支。
- **失败 · 执行方法错误**：Processed 0 / 类型没变 / 建图失败 / 量化 OOM。
  ⇒ **修方法重跑，判据不变**。
- **失败 · 方向错误**：G3 全过（类型确实全变对称）但 Δ 落在 |Δ|<0.005
  ⇒ 这**不是**执行错误，是 H-sym-FC 本身被否定，按 4.3 结案。

## 7. 无论成败都要沉淀的可复用结论（主线 B，`../docs/QNN_CONVERSION_GUIDE.md`）

1. `--quantization_overrides` 会把浮点位宽默认降到 16 —— 必须显式 `--float_bitwidth 32`
2. overrides 必须用 ONNX 名；`Processed N` 必须每次 grep
3. 「只对某类算子改量化 schema」的通用做法：从"全局改一版"的 DLC 里**取 SDK 自算的 encoding**，
   再用 overrides 选择性回灌 —— 避免自己推量化器的取整公式
4. OpDef 支持表必须在改 schema **之前**查（FC 收 SFxp8、RmsNorm 不收）

## 9. 主结果

真值 = FP32 onnxruntime；口径 = 主体（`|a| ≤ p99`，能量集中度 99.83% ⇒ 全量口径不可用）。

| 配置 | E_all | E_bulk | **cos_bulk** | slope_bulk | 主体 std |
|---|---|---|---|---|---|
| FP32 真值 | — | — | 1.0000 | 1.0000 | 0.6235 |
| CPU 参考 · 基线 | 1.1757% | 7.0863% | 0.9975 | 1.0057 | 0.6286 |
| **CPU 参考 · 对称 FC** | 1.4260% | 8.9153% | **0.9961** | 1.0007 | 0.6264 |
| 设备 HTP · 基线 | 19.2406% | 114.798% | **0.6033** | 0.8622 | 0.8910 |
| **设备 HTP · 对称 FC** | 21.0129% | 125.825% | **0.5507** | **0.8217** | 0.9303 |

**判据 4.3：`Δ = 0.5507 − 0.6033 = −0.0526` ≤ −0.005 ⇒ 落入「反向恶化」分支
⇒ H-sym-FC 被否定。**

- 幅度参照：无效变更的本底是 ±0.001（O=3 实测 Δ=−0.0005）⇒ 本次是本底的 **105 倍**，不是噪声。
- **判据 4.4（次判据）同样朝坏的方向**：slope 0.8622 → **0.8217**，
  即"HTP 把幅值系统性算小"**没有被修复，反而更重**（增益误差 13.8% → 17.8%）。
- 判据 4.5（CPU 对照）✅ 通过：0.9961 ≥ 0.99 ⇒ 对称化**本身没把模型改坏**。

## 10. 关键对照：同一个改动，HTP 的损失是 CPU 的 37.6 倍

| | Δcos_bulk |
|---|---|
| SNPE CPU 参考 | **−0.0014** |
| 设备 HTP | **−0.0526** |
| 倍数 | **37.6×** |

宿主侧还量化了这次改动在**权重表示层面**的代价（`scripts/repr_cost_sym.py`，59 个全测）：
权重自身量化表示误差中位 **3.73% → 3.97%**（+6.5% 相对），
**scale 变粗中位 1.073 倍、最大 1.548 倍**（权重能量集中度仅 11.11%，两口径互相印证）。

⇒ ①事实：一次**在 CPU 上几乎无害**（Δcos −0.0014）的权重 encoding 改动，
   在 HTP 上造成 **37.6 倍**的损失。
⇒ ②推论：**HTP 对权重量化步长/表示质量的敏感度远高于 CPU 参考**，
   与 #39（HTP 引入超出正确定点的误差）同向。

## 11. 本实验**不能**得出的结论（约束 2，明确划界）

对称化同时做了**两件事**：① 消掉 offset 项（`z_w = 0`）② 把 scale 粗化中位 7.3%。
本实验**无法分离**这两者，因此：

- ✅ 能说：**"通过对称化 FC 权重来修 HTP"这条路径被否定**（净效应是恶化 37.6 倍于 CPU）。
- ❌ **不能**说："offset 项的灾难性抵消机制不存在"——
  #40 的实测（offset 项/主项 = 0.891~0.979）仍然成立，
  只是**消除它的收益（若有）小于 scale 粗化的代价**，或被 HTP 对步长的敏感性淹没。
- ❌ **不能**说 E_bulk "从 114.8% 涨到 125.8% 是恶化 11pp"——
  两者都 >100%（约束 7：大误差之间比大小无意义）。**结论只由余弦支撑。**

误差方向：`cos∠(误差_基线, 误差_对称) = 0.5895` ⇒ 两次的误差**部分同向但不重合**，
不是"同一个误差加大"，而是被扰动到了另一个同样错的位置。

## 12. 与官方文档的冲突（**必须记录，防止后人重试**）

官方 `htp_backend.html` 通用最佳实践写的是
*"It is **recommended** to always use symmetrical quantization of weights ...
to obtain best accuracy on HTP based targets."*
本项目**实测结果与之相反**：在 A16W8 + DiT（零 Convolution、99.99% 权重在 FC）这一配置下，
对称权重让设备侧主体余弦从 0.6033 掉到 0.5507。

⇒ 该建议**在本配置下不成立**。它可能是针对 Conv 类网络或 A16W16 的经验。
**不要因为"官方推荐"而再试一次**——完整代价是 1 次转换 + 54 分钟量化 + 12 分钟建图 + 设备实测。

## 13. 本实验指向的下一步

`Δcos_htp / Δcos_cpu = 37.6` 说明 HTP 的误差**对权重量化质量高度敏感**。
本次是把 scale 变**粗**（1.073×）⇒ 更差；
⇒ ③假设（**未验证**）：把 scale 变**细**应当有收益。
⇒ 直接指向台账 **#47 `--use_per_row_quantization`**（官方帮助原文：
   *"enable rowwise quantization of **Matmul and FullyConnected** ops"*），
   逐行量化会让每一行用自己的 scale，中位数上显著变细，且**不改图、只需重量化**。
   这条现在有了本实验提供的定量动机，优先级应升到第 1。
