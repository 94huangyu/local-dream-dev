# EXP_PLAN_VS_FP32 —— HTP 是"算错了"，还是"另一种同样合法的舍入"？

定稿时间：2026-08-15（执行前定稿，判据不得事后修改）
前置：`EXP_PLAN_CH85_CAUSAL`（弥散本底是主因，差异为计算过程差异而非量化表示差异）
主线归属：A → C 的机制层

## 0. 为什么必须先问这一句

到目前为止所有比对的基准都是 **SNPE CPU 参考**，并**默认它是对的**。
这个默认有依据（Test B 用它出清晰的猫），但**从未直接验证过它在张量层面接近 FP32**。

存在两种性质完全不同的可能：

| 可能 | 含义 | 该走的路 |
|---|---|---|
| **甲：HTP 算错了** | CPU 接近 FP32，HTP 远离 FP32 | 查 HTP 算子实现 / 报 SDK bug / 换精度配置 |
| **乙：两者都只是量化噪声的不同实现** | CPU 与 HTP 离 FP32 差不多远，只是方向不同 | **模型本身对量化过于敏感**，要改量化策略而不是查 HTP |

**甲和乙的下一步完全相反。** 在分清之前投入任何重量化/重建（数小时起）都是赌博。

## 1. 预期结果（假设）

**H-甲**：CPU 参考显著更接近 FP32；HTP 显著更远。

零假设 H-乙：两者与 FP32 的距离同量级（相差 < 1.5 倍）。

## 2. 实现路径（一次 onnxruntime 运行，零设备成本）

用 `transformer_part1b.onnx`（FP32）跑一次，输入取 **testB s0 的 CPU 参考上游输出**
——即与"实验 A 隔离 part1b"**完全相同的输入**。

得到 `U_fp32`，与已有的两份对比：
- `U_cpu`：SNPE CPU 参考跑量化 `.dlc`（`testB/s0_transformer_part1b/out/Result_0/unified.raw`）
- `U_htp`：设备 HTP 跑 `.bin`（`htp_vs_cpu/A_part1b/unified.raw`，已确认与设备在线建图逐位相同）

指标：相对 L2、余弦；并算 **夹角关系**——`U_cpu−U_fp32` 与 `U_htp−U_fp32` 两个误差
向量的夹角余弦，用于区分"同向放大"与"各自独立的噪声"。

## 3. 验收标准（判据，事后不得修改）

设 `E_cpu = ||U_cpu − U_fp32|| / ||U_fp32||`，`E_htp = ||U_htp − U_fp32|| / ||U_fp32||`。

**判据 1（主判据）**：
- `E_htp / E_cpu > 2.0` ⇒ **【甲】HTP 显著更远离 FP32，是 HTP 算错**
  ⇒ 下一步查 HTP 算子实现 / 精度配置，方向正确。
- `E_htp / E_cpu < 1.5` ⇒ **【乙】两者同量级**
  ⇒ **HTP 不算"错"，是模型对量化过于敏感**；
     下一步应改量化策略（提高 act_bitwidth、per-channel、混合精度），
     **不要**再去查 HTP 算子实现。
- 落在 1.5~2.0 之间 ⇒ 证据不足以区分，需补做 part2 的同类对照再判。

**判据 2（误差方向）**：算 `cos∠(U_cpu−U_fp32, U_htp−U_fp32)`。
- 接近 1 ⇒ 两者误差同向，HTP 像是"CPU 误差的放大版" ⇒ 支持同一机制、程度不同。
- 接近 0 ⇒ 两者误差正交，是**互相独立**的两种误差源 ⇒ 支持"不同实现各自舍入"。
此判据**不单独定结论**，只用于解释判据 1。

**判据 3（有效性自检）**：`E_cpu` 必须是有限的合理值（< 100%）。
若 `E_cpu` 本身就极大，说明 FP32 参考跑错了（输入不匹配/onnx 版本不对），
本次无效，不得解读。

## 4. 成功 / 失败判断

- **成功**：拿到 `E_cpu`、`E_htp` 与夹角，按判据 1 给出明确分支。
- **失败·执行方法错误**：onnxruntime OOM / 输入名对不上 / 输出名对不上。
  ⇒ 修方法重跑，判据不变。
- **失败·方向错误**：`U_fp32` 与 `U_cpu` 逐位相同 ⇒ 说明误把量化结果当 FP32 读了，必须查清。

## 5. 预算与放弃条件

- 预算：1 次 onnxruntime 运行（part1b FP32，`.onnx` + 外部权重）。
- 若 OOM 跑不动 part1b，退而用 part1a（差异 2.35%，信号弱但同样能判甲/乙）。

# 执行结果（2026-08-15，判据未做任何修改）

脚本 `scripts/vs_fp32.py`。FP32 参考由 `transformer_part1b.onnx` + onnxruntime CPU 跑出，
输入与"实验 A 隔离 part1b"逐字节相同。产物 `p0_experiments/vs_fp32/unified_fp32.raw`。

## 判据 3（有效性自检）：✅ 通过
`E_cpu = 1.1757% < 100%`，且 `U_fp32` 与 `U_cpu` 不逐位相同。

## 实测数据（基准 = FP32）

| 量 | 值 |
|---|---|
| FP32 std | 14.9664 |
| CPU 参考 std | 15.1097 |
| **HTP std** | **12.9183** |
| **E_cpu（CPU 参考 vs FP32）** | **1.1757%** |
| **E_htp（设备 HTP vs FP32）** | **19.2406%** |
| 参考：HTP vs CPU | 19.4727%（与先前实测一致） |

## 判据 1：🔴 **【甲】HTP 算错了**

`E_htp / E_cpu = 16.366`，远超判据阈值 2.0。

⇒ ②严格推论：**量化模型本身没问题——SNPE CPU 参考把它跑到了距 FP32 仅 1.18%
（正常的量化噪声量级）。而 HTP 跑同一个模型，距 FP32 达 19.24%，是 CPU 的 16.4 倍。**

⇒ 这不是"两种同样合法的舍入"，**HTP 的执行是实打实的错**。
⇒ 下一步查 HTP 算子实现 / 精度配置，方向正确。
⇒ 同时也**再次确认了"CPU 参考可当真值"这个此前一直是默认、从未验证的前提**
   （1.1757% 就是它的实测精度）。

## 判据 2（误差方向）：cos∠ = **-0.3293**

两个误差向量**部分反相关**，不是同向放大。
结合 std 的系统性收缩（HTP 12.92 vs FP32 14.97，仅 **86.3%**），
以及 15.8 节 ch85 处 HTP 给出 CPU 值 **55.8%** 的观察：

⇒ ②推论（**待验证**）：**HTP 系统性地把幅值算小**，且幅值越大压得越狠。
   形态上像是重量化 scale 偏小或存在饱和/截断，而不是随机舍入噪声。

## 附带：量化 encoding 的条件数很差（①实测，可能与 HTP 的余量有关）

`unified` 的 encoding 是 min-max 校准的结果：`[-145.277, 6265.993]`，scale 0.0978，bw 16。
但张量主体 std 只有 **15.11**：

| 主体范围 | 占用量化级数 | 占总级数 | 有效位宽 |
|---|---|---|---|
| ±1σ | 308.9 | 0.471% | **8.27 bit** |
| ±3σ | 926.7 | 1.414% | **9.86 bit** |
| ±6σ | 1853.4 | 2.828% | 10.86 bit |

**16 bit 的量程里，主体只用到约 10 bit**——其余全被 0.026%（4129 个）超 6σ 的离群值占掉。

⇒ ②推论（**待验证**）：encoding 条件数差本身不致命（CPU 参考在同一 encoding 下只差 1.18%），
   但它可能**吃掉了 HTP 内部的数值余量**，使 HTP 的实现缺陷被放大。
   若成立，`--act_quantizer_calibration percentile` 收紧量程可能是可行的缓解手段
   （p99.99 定量程可把 scale 收紧 3.6 倍）。**这条尚未验证，且需重新量化，成本数小时。**
