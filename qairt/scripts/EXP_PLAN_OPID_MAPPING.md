# EXP_PLAN_OPID_MAPPING —— 把 `OpID: 0x6994000000a2` 映射到具体算子/张量

定稿时间：2026-08-14（执行前定稿，判据不得事后修改）
主线归属：A（排查设备失败）→ 假设 C「HTP 执行 ≠ CPU 参考」下唯一在手的硬线索

## 0. 执行前新增的实测事实（本次开工时从既有日志读出，非本实验产物）

三份**已存在**的构建日志，同一个 OpID，报告的 scale 值**并不相同**：

| 日志 | 目标 | DLC | 报告值 |
|---|---|---|---|
| `ZImage_QNN_Evidence\dlc_pipeline\transformer_part2\03_context_binary_generator.log:8` | sm8550 | 原始 | `inf` |
| `sm8750_retarget_all.log:496` | sm8750 | 原始 | `inf` |
| `p0_experiments\maskfix\03_ctxgen.log:8` | sm8750 | **maskfix** | **`1000000.000000`** |

⇒ ①实测数据。`val_104` 掩码修复把该 OpID 处的 scale 从 `inf` 变成了有限的 `1e6`。
⇒ ②严格推论。14.18/14.21 记载的「该 inf **不能**由单个张量的 encoding 解释」**不成立**：
   证据恰好相反——那个张量的 encoding 直接控制着该处的量级，只是改完仍未低于 SDK 阈值。
   （原判据 2「错误消失」确实没通过，这一点记载无误；被推翻的是从中推出的**归因结论**。）

本实验正是建立在这条新事实上：`1e6` 是一个**可离线复算的具体数值**，
比「某处有个 inf」强得多，可以直接用来在图上定位。

## 1. 预期结果（假设）

**H1（主假设）**：QNN HTP 的 `OpID` 低 32 位 = DLC 图中算子的 `Id` 序号。
  `0x6994000000a2` → `0xa2` = **162** → `snpe-dlc-info` 转储里 `Id=162` 那一行。
  高 16 位 `0x6994` 为 graph/context 标识，与算子无关。

**H2（独立佐证假设）**：出问题的那条边，其 `scale_in / scale_out` 比值在
  **原始** DLC 中为 inf（或分母为 0），在 **maskfix** DLC 中**恰为 1e6 量级**。

H1 与 H2 相互独立：H1 靠编号，H2 靠数值。两者指向同一个算子即互为验证。

## 2. 实现目标

拿到该算子的：`Id` / 算子名 / 算子类型 / 输入张量名 / 输出张量名 / 两侧 encoding（bitwidth, min, max, scale, offset）。
**只求身份，不求修复方案。**

## 3. 实现路径（全部离线，零构建成本）

1. 写 `scripts/map_opid.py`，直接解析 `snpe-dlc-info` 转储的表格
   （`Id | Name | Type | Inputs | Outputs | ... | Parameters`，含续行合并）。
   **不经 ONNX**——转储是契约的唯一合法来源（CLAUDE.md 约束 3）。
2. 对 `maskfix_part2_dlcinfo.txt` 与 `transformer_part2_dlcinfo.txt`（原始）各建一份
   `Id -> {name, type, inputs, outputs, encodings}`。
3. 检验 H1：打印两份转储的 `Id=162`。
4. 检验 H2：对**每个**算子计算 `max(scale_in/scale_out, scale_out/scale_in)`，
   全图排序；在原始转储里找比值为 inf/除零的算子，在 maskfix 转储里找比值 ≈1e6 的算子。
   **独立于 H1 地**给出候选清单。
5. 交叉：H1 的 162 是否出现在 H2 的候选里。

> 注：既有的 `scripts/scan_requant_ratios.py` **不能直接复用**。它的正则
> `([A-Za-z_][A-Za-z_0-9]*) encoding` 不允许张量名含点，会静默漏掉所有
> `layers.15.xxx.weight` 这类权重张量（14.18 称"已修正为允许含点"与文件现状不符）。
> 本实验自带解析器，并在报告里说明该差异。

## 4. 验收标准（判据，事后不得修改）

**判据 1（H1 成立）**：`Id=162` 的算子存在，且其类型/位置与 `q::Requantize` 相容
（即它是一个会在量化图上产生重量化的算子，或其输入输出 scale 明显失配）。

**判据 2（H2 成立）**：全图比值扫描中，maskfix 侧存在比值落在 `[1e5, 1e7]` 的算子；
且同一算子在原始侧比值为 inf 或分母为 0。

**判据 3（定位成功 = 本实验的真正成功条件）**：判据 1 与判据 2 指向**同一个算子**，
且该算子在 maskfix 侧的比值在 `[1e5, 1e7]` 内、在候选中**唯一或可排他地最大**。

- 三条全过 ⇒ 算子身份确定，实验成功，可以进入"为什么它的 requant 是 inf"这一步。
- 判据 2 过、判据 1 不过 ⇒ 身份仍确定（数值证据独立成立），但 OpID 编码规则的
  推测被否定，须在文档中记为"OpID 低位≠Id，编码规则未知"。
- 判据 2 不过 ⇒ 本路径失败，**转 fallback**（见第 6 节），不得强行解释。

## 5. 成功 / 失败的判断依据

- **成功**：能写出一句有证据支撑的话——"`0x6994000000a2` 是算子 X（类型 T），
  边 `A -> B`，原始 scale 比值 inf，maskfix 后 1e6"，且每个数字都能指回转储的行。
- **失败且方向错误**：全图**没有**任何算子的比值落在 1e6 附近 ⇒ 报错里的 "scale" 不是
  相邻张量 scale 之比，我对该错误的力学理解是错的 ⇒ 必须回到主线重新理解该错误。
- **失败且执行方法错误**：解析器漏行/漏张量（可用"转储里算子总数 vs 表格行数"自检）
  ⇒ 修解析器重跑，不改判据。

## 6. Fallback（仅当判据 2 不过才启动）

按 14.20 原案：`--log_level verbose` 重跑 maskfix DLC，跑到错误出现（约 5.2 分钟，
实测第 310647 ms）即终止；再不行则按 15 个 block 二分裁剪 ONNX。
**先做零成本的离线扫描，再花 5 分钟的构建**——顺序不能反。

## 7. 深度预算与放弃条件（MAINLINE 规则 2）

- 预算：离线扫描 1 轮；不成则 verbose 1 轮（5 分钟）；再不成则二分 4 轮（20 分钟）。
- 放弃条件：以上全部用尽仍拿不到算子身份，**回主线**重新评估"编译期报错"这条线
  是否真的与"橙色色块"有因果关系——注意该报错**不阻断构建**（`EXIT=0`，
  2.9 GB 的 `.bin` 正常产出），它是否影响数值输出**尚未验证**。

# 执行结果（2026-08-14，判据未做任何修改）

执行工具：`scripts/map_opid.py`（自带解析器，纯离线，无构建开销）。
fallback 未启动——离线扫描一轮即定位成功，`--log_level verbose` 与二分裁剪都没有用到。

## 判据逐条结论

| 判据 | 结果 | 依据 |
|---|---|---|
| 判据 1（H1：OpID 低位 = Id） | ❌ **不通过，H1 被否定** | `Id=162` 是 `node_linear_12_post_reshape`（`Reshape`），与 requant 无关 |
| 判据 2（H2：数值定位） | ✅ **通过** | 唯一命中：`Id=66 node_Where_105`，maskfix 比值 ≈1e6、原始侧 inf |
| 判据 3（两者同指一个算子） | ❌ 不通过 | 按第 4 节预案：**身份仍确定**（判据 2 独立成立），H1 记为否定 |

⇒ 按第 4 节写死的预案分支「判据 2 过、判据 1 不过 ⇒ 身份仍确定，但 OpID 编码规则的推测
被否定」执行。**`OpID 低 32 位 ≠ dlc-info 的 Id`，QNN 的 OpID 编码规则仍未知。**

## 定位结果：`OpID: 0x6994000000a2` = `node_Where_105`

DLC 图内 `Id=66`，类型 `Eltwise_Ternary`（ONNX `Where`），是 part2 **全图唯一**的三元算子。

```
输入  unsqueeze_4  Bool_8   [1,1,1,4128]  NATIVE   （无 encoding）
输入  val_103      uFxp_16  [1]           STATIC   range=[0, 1e-4]        scale=1.5259e-09
输入  val_104      uFxp_16  [1]           STATIC   range=[-100, 0]        scale=1.5259e-03   <- maskfix 改过
输出  val_105      uFxp_16  [1,1,1,4128]  NATIVE   range=[0, 1e-4]        scale=1.5259e-09
```

## 定位为什么可信：两点精确复算，不是"量级相符"

报错里的 scale = `scale(val_104) / scale(val_105)`，两个版本各复算一次，与日志逐位吻合：

| 版本 | val_104 scale | 复算比值 | float32 后 | 日志实际打印 |
|---|---|---|---|---|
| 原始 | 3.40282346638528859811704183484516925440e38 / 65535 = 5.192376e33 | 3.4028234663852886e**42** | **inf**（超 float32 上限 3.4028235e38） | `inf` |
| maskfix | 100 / 65535 = 1.5259021896696422e-03 | 100 / 1e-4 = **1000000.0** | 1000000.0 | `1000000.000000` |

两个独立数据点、零自由参数，**精确**命中（第二点连有效数字都对上）。
转储只打印 12 位小数，直接用打印值算会得到 999936——这是打印截断，用精确值
（`100/65535` 与 `1e-4/65535`）算即为整 1e6。

排他性：全图比值落在 [1e5,1e7] 的还有 10 个 `FullyConnected`（权重 bw8 vs 激活 bw16，
正常现象），但它们在原始/maskfix 两份转储里**数值完全相同**，无法解释一个
从 inf 变成 1e6 的量。**只有 `node_Where_105` 变了。**

## 顺带确定的第二件事：为什么 maskfix 没能消掉报错

`val_104` 改了，但 `Where` 的**输出** `val_105` 的 encoding **没跟着改**，仍是 `[0, 1e-4]`。
一个 offset=0 的无符号 uFxp_16、区间 `[0, 1e-4]`，**根本无法表示任何负数**。

⇒ 14.18/14.21 的结论「该 inf 不能由单个张量的 encoding 解释」，**方向对但归因错**：
它确实不是**单个**张量的问题，但它完全是**张量 encoding** 的问题——是
`(val_104, val_105)` 这**一对**，修复只动了其中一个。

## 对照组（part1a/part1b，编译干净）

| 图 | Where 数 | 输出区间能否容纳掩码分支 | 编译 |
|---|---|---|---|
| part1a | 1（`node_where_1`） | ✅ 掩码分支 min=-1.68，输出 min=-18.54，**可表示** | 干净 |
| part1b | 0 | — | 干净 |
| part2 | 1（`node_Where_105`） | ❌ 掩码分支 min=-100，输出 min=**0** | **报错** |

对照成立：唯一有此病理的图，正是 8 图中唯一报算子级错误的图。

## 【关键】差异 ≠ 根因：本次的证伪

`val_105` 经 `Add` 进入 part2 **全部 15 个注意力块**（`node_Add_107` … `node_Add_1815`）
再进 `Softmax`。看起来足以解释"语义结构被抹掉"。**但实测否定了这条因果**：

```
testB/s0_transformer_part2/unified_mask.raw  (4128 个 float32)
  取值集合 = {1.0}      ==0 的个数 = 0
```

**该 prompt 下 `unified_mask` 全为 1，没有任何被掩码的位置。**
⇒ `Where` 在全部 4128 个位置上都选 `val_103`(≈0) 分支，`val_104` 分支**一次都没被选中**。
⇒ 这个不可表示的掩码常量位于**死路径**上，对本输入的输出没有影响。

而且这份 `unified_mask.raw` 正是 **Test B 出好猫那次**所用的输入，
即：出好图的配置下，这条路径同样是死的。

⇒ ②严格推论：**该编译期报错很可能是"橙色色块"的红鲱鱼**，
   不能作为根因；它是一个**真实但当前未被触发**的潜在缺陷
   （换一个需要 caption padding 掩码的 prompt 就会被触发）。

注：caption 侧的 padding 确实存在（`cap_pad_mask` 32 个里 20 个是 0），但它在
**part1a** 用 `node_where_1` 以 `cap_pad_token`（一个真实的学习到的 pad embedding）
**替换**掉了，不靠 part2 的注意力掩码处理；part1a 那个 Where 的 encoding 是健康的。

## 本实验的成败判定（对照第 5 节）

- **成功**：拿到了算子身份，且每个数字都能指回转储行号与日志行号。
- 但**主线上是一次证伪**：拿到身份后立刻发现这条线索指向死路径。
  这正是第 7 节放弃条件里预写的情形——**回主线**，不要在这条线上继续深挖。

## 遗留的、真正该问的下一个问题（尚未验证）

Python 参考侧喂给 part2 的 `unified_mask` 全为 1。
**设备上的 C++ 实现喂进去的 `unified_mask` 是什么？** 尚无证据。
若 C++ 侧喂进了含 0 的掩码，则死路径**在设备上是活的**，上面的证伪不适用于设备，
且此时 `val_105` 的病理 encoding 会真实生效。这是一个廉价且能直接分叉主线的检查。
