## 三、实现路径（**按序，不许跳步**）

### 步 0　装置自检（宿主 + 设备各约 2 分钟，**先于一切测量**）

按约束 8：**量测装置先用已知样本验证，再拿去测未知。**

| 检查 | 做法 | 通过条件 |
|---|---|---|
| 0a 热传感器可读 | `cat /sys/class/thermal/thermal_zone*/type` 与 `.../temp` | 非 root 可读，且能找到 NPU 相关分区（#141 见过 `nsphmx-*`）。**读不到则改用固定静置，见 §3.2** |
| 0b 记录空闲基线温度 | 设备静置状态下采一次全部分区 | 得到 `T_idle`（每分区一个数） |
| 0c **VmHWM 语义自证** | 一次生成中同时 ① 1 Hz 轮询 `VmRSS` ② 结束后读 `VmHWM` | **`VmHWM ≥ max(轮询 VmRSS)`**。不成立 ⇒ VmHWM 不可用，只用轮询峰值 |
| 0d 后端进程是同一个 | 生成前后 `pidof libstable_diffusion_core.so` 一致 | 一致（否则 VmHWM 跨了进程，无意义） |

🔴 0c 是**必须**的：VmHWM 是「进程有史以来的峰值」，若跨多次生成累积，
它测的就不是「一次生成的峰值」。**用 force-stop 使每次测量对应一个全新进程**（见 §3.2）。

### 步 1　基线测两次（**这就是协议验证，不是额外开销**）

每次测量的**完整口径**（此即待验证的协议）：

1. `am force-stop` 杀掉 app ⇒ 后端进程一并消失 ⇒ VmHWM 归零重来
2. **等到冷机**：所有热分区回到 `T_idle + 3 °C` 以内（0a 失败则改为**静置 15 分钟**）
3. 重新拉起 app，等 8081 监听（此段**不计时**）
4. 发一次 `/generate`（**固定 prompt、固定 seed=777**），记录：
   - **主时钟**：`curl` 的 `time_total`（🔴 **事前指定为主判据**）
   - 交叉核对：logcat 墙钟 `Req Rcvd` → `complete`；app 自报耗时
   - **峰值 RSS**：`VmHWM` + 1 Hz 轮询序列（两者都记）
   - 起止温度
5. 记录出图 **sha256**

得 `B1`、`B2` 两组数。**两次之间必须完整走一遍第 2 步的冷机等待。**

### 步 2　🔴 门 G0 —— 内存可行性（**零代码改动，在 B1/B2 的数据上算**）

方案 A 的峰值已经包含「part1a+1b + **一个** part2 半段」。
方案 B 的增量 = **另一个半段**。取两个半段中较大者（part2b，1,465,870,912 B = 1.398 GiB）：

```
预测方案B峰值 = 实测方案A峰值RSS + 1.398 GiB
```

⚠️ 这是**下界估计**：常驻还会多出各自的 I/O 张量与 scratch，不会更少。

**否决条件（事前锁定）**：
- 预测峰值 ≥ **7300 MB**（#16 实测杀线）⇒ **F 直接否决，不改代码、不上机**

> 这一条就是约束 4·补的代价门：**改动的代价先在便宜的地方算出来，别拿设备去撞。**

## 四、判据（🔴 事前锁定）

### G1　协议是否可信

```
|B1 − B2| / mean(B1, B2)  ≤ 3%   ⇒ 🟢 协议成立，可用于判 F
                        ∈ (3%, 8%] ⇒ 🟡 协议弱：只有当 F 的效应 > 3× 该值时才可判
                        > 8%       ⇒ ❌ 协议不成立，M1 的结论作废，本轮只报 G0 与内存
```

**3% 的来源（不是拍脑袋）**：要判的效应是 −26%，#141 实测热漂移是 +16%；
判据必须显著小于二者。3% 使 F 的效应有约 9 倍余量。

### G2　速度收益

以 `mean(B1,B2)` 为基线：

```
M1 比基线快 ≥ 15%   ⇒ 🟢 有效
快 3%~15%           ⇒ 🟡 有效但低于预期，须查为什么（加载并非纯串行开销？）
|Δ| < 3%            ⇒ ❌ 无收益 ⇒ 说明「加载耗时」的模型是错的，回头查 #132 的斜率截距法
M1 比基线**慢**      ⇒ ❌ 且是异常，必须查清（常驻不该变慢）
```

### G3　精度（🔴 **不是权衡项，是 bug 判据**）

```
出图 sha256(M1) == sha256(B1) == sha256(B2)   ⇒ 🟢
不相同 ⇒ ❌ **这是 bug，不是「收益/代价权衡」**
```

理由（沿用 `EXP_PLAN_SPEED.md` §三，不得放宽）：同一个 context、同一份输入，
常驻与否**在数值上应当逐位相同**。方案 A 交付时实测确实相同。
不同 ⇒ 说明常驻引入了状态污染，必须查清再谈速度。

⚠️ 若 sha256 不同，**不许**退而用「L1/L2/L3 在噪声内」来放行——那是把 bug 洗成权衡。

余量 < 400 MB                                   ⇒ 🟡 实验室可行，不交付

## 八、实测结果（2026-08-29 当晚，判据未作任何修改）

### 8.1 三次基线

| tag | 主时钟 `time_total` | ION 峰值 | 峰值时 MemAvailable | NPU 峰值 | png sha256 |
|---|---|---|---|---|---|
| B1（试跑，旧装置） | **202.486 s** | 未测到 | — | 未采 | `5ce17d9a…a3a21c` |
| **B2** | **204.094 s** | **7,375,036 kB (7202 MiB)** | 980 MiB | 103.4 °C | 同上 |
| **B3** | **204.405 s** | **7,375,036 kB (7202 MiB)** | 855 MiB | 103.4 °C | 同上 |

三次 sha256 完全相同；B2/B3 的 ION 峰值**逐字节相同**。

### 8.2 G1（协议）🟢 PASS

```
|B2 − B3| / mean = 0.152%      阈值 3%
含试跑 n=3 极差 1.919 s = 0.94%
```

⇒ **#133 的「8% run-to-run 噪声」被证否**（低 50 倍）。那 8% 来自 prompt / 热 / 后台三者同时变化。

### 8.3 G0（内存）❌ 否决 —— 未改一行代码

步循环内 ION 是干净的两电平方波（B3，1 s 分辨率）：

| 电平 | 采样点 | 含义 |
|---|---|---|
| 5212 MiB | 79 | part1a+1b 常驻，part2 未加载 |
| 7148~7202 MiB | 56 | 上面 + **一个** part2 半段 |

⇒ 每个 part2 半段实测占 ION **1936~1990 MiB**。

```
方案 B 预测峰值 ≈ 5212 + 1936 + 1990 ≈ 9138 MiB
额外需求            ~1936 MiB
峰值时可用          855~980 MiB
缺口                ~1000~1100 MiB     ⇒ 否决
```

🔴 **判据操作化的自我订正（约束 8）**：§3.2 原写「预测峰值 ≥ 7300 MB 则否决」，
而实测**方案 A 自己就是 7202 MiB** ⇒ 按那条线，已交付且稳定运行的方案 A 也会被判死
⇒ ②**#16 的 7300 MB 不是 ION 口径，拿它做阈值是无效操作化**。
上面的否决**不使用该阈值**，只用同一次测量里的两个数（额外需求 vs 峰值可用），论证自足。

### 8.5 🔴 首版量测装置量错了口径

进程 `VmRSS` 生成全程仅 **~200 MiB**，峰值 **2356 MiB** 只出现在
「把 `.bin` 读进 CPU 缓冲区」那一瞬（≈ part1a 文件 2263 MiB），交给 DSP 后立即释放
⇒ **context 常驻在 DSP/ION 侧，进程 RSS 根本看不见它**。改用 `/proc/meminfo` 的 `IonTotalUsed`。

附带：`VmHWM` 出现过**小于**瞬时 `VmRSS`（2,412,344 < 2,412,992 kB），
原因是内核 `update_hiwater_rss()` 惰性更新 ⇒ 不能当唯一峰值来源。

⚠️ **协议纪律上的一处自我修正**：B1 与 B2 之间换了装置 ⇒ `|B1−B2|` 同时含协议噪声与装置差异，
**不可用于 G1**。故补跑 B3，G1 改用装置相同的 **B2 vs B3**。

### 8.7 顺带的热发现（已同步 #144，机制描述与 #141 需对齐）

**单张图内 NPU 就冲到 103.4 °C**（起点 48~50 °C），步循环内在 60~103 °C 间剧烈摆动。
⇒ ②#141 的「连续 6 张 +16%」不是 NPU 慢慢热起来（单张已打满热区）；
③累积在哪（外壳/电池/PMIC）**未实测**。
①冷机恢复：58.8 → 46.1 °C 约 **6 分钟**。
