# EXP_PLAN_LAYER_LOCALIZE —— 定位 HTP 从**哪个算子**开始偏离

定稿时间：2026-08-15（执行前定稿，判据不得事后修改）
主线归属：A → C 的机制层。**这一步应当排在任何修复尝试之前。**

## 0. 为什么必须先做这个（自我纠偏）

已确立：HTP 跑 part1b 的输出距 FP32 **19.24%**，CPU 参考仅 **1.18%**。
但 part1b 有 **626 个算子**，我**不知道偏差从哪一个开始**。

在没有定位的情况下去改量化配置（对称权重 / percentile / A16W16），
是"基于违反了某条建议就去试"，**不是"基于测到了它是原因"**。
本项目已因这个模式浪费过两轮（`add_138`、`mul_107` 的 float fallback，见 CLAUDE.md 约束 2）。

**另有一个数据不支持"精度不够"这一类解释**：HTP 误差是 **7.31 个量化步**，
而理想舍入只有 0.45 步——误差比量化分辨率**大 16 倍**。
调 schema / 调量程属于改分辨率，**很可能打不中**。

## 1. 工具可用性（已核实）

`qnn-net-run --debug`：「output from all layers of the network will be saved」。
限制：**不能与 `--retrieve_context` 同用**，但**可与 `--dlc_path` 同用**。

关键前提（**已实测**，`EXP_PLAN_ONDEVICE_PREPARE`）：
`--dlc_path` 在设备上在线建图的输出与宿主编的 `.bin` **逐位相同**
（相对 L2 = 0.0000%，最大差 = 0）。
⇒ **用 `--dlc_path --debug` 得到的逐层结果，可以合法地代表 `.bin` 的行为。**

CPU 参考侧：`snpe-net-run` 的 `%` 前缀可导出任意中间张量
（`../docs/EXECUTION_MODEL.md` 规则 5，已实测），走 `scripts/snpe_runner.py` 的 `want` 参数。

## 2. 实现路径

1. 设备：`qnn-net-run --dlc_path part1b.dlc --backend libQnnHtp.so --debug`
   （在线建图约 16 分钟）→ 全部逐层输出留在设备上。
2. 列出产出的张量名与文件大小（不全量拉回，39 GB 级别）。
3. 宿主：用 `snpe_runner.py` 一次性请求**同名张量**，得到 CPU 参考的逐层值。
4. **二分定位**：先取沿图均匀分布的 ~8 个张量比对，找到"相对误差从小跳到大"的区间，
   再在区间内细分。每个张量 63 MB，拉回约 2 秒，二分成本极低。
5. 对定位到的算子，记录：算子类型、输入/输出 encoding、该处的相对误差跳变幅度。

## 3. 验收标准（判据，事后不得修改）

**判据 0（有效性）**：设备侧 `--debug` 必须真的产出多个中间张量文件
（数量 > 10），且其中"图的正式输出 `unified`"与既有 `A_part1b/unified.raw`
**逐位相同**（证明这次运行与之前那次等价，比对才有意义）。
不满足 ⇒ 本次无效。

**判据 1（定位）**：给出**第一个**满足下列条件的算子 X：
其输出的 HTP-vs-CPU 相对误差 ≥ 5%，而它**所有输入**的相对误差均 < 2%。
- 找到唯一的 X ⇒ **定位成功**，X 即偏差的引入点。
- 找到多个互不相邻的 X ⇒ 偏差有**多个独立引入点**，全部列出，
  并按各自误差跳变幅度排序。
- 找不到任何 X（误差从第一层起就均匀累积）⇒ **不存在单一引入点**，
  是全局性的实现差异；此时**才**回到"改全局配置"这条路，且结论要写明。

**判据 2（形态）**：对定位到的 X，报告其误差是**增益型**（斜率偏离 1）
还是**噪声型**（斜率≈1 但残差大）。这决定后续该查什么。

**判据 3（自检）**：逐层相对误差序列应当**单调不减或接近单调**（误差不会凭空变小）。
若出现大幅回落，说明比对配错了张量（张量名对不上/形状不对），本次无效。

## 4. 成功 / 失败判断

- **成功**：拿到算子 X 的身份 + 误差跳变数据，或明确判定"无单一引入点"。
- **失败·执行方法错误**：`--debug` 与 `--dlc_path` 不兼容 / 设备存储不足 /
  张量名在两侧对不上。⇒ 修方法重跑，判据不变。
- **失败·方向错误**：CPU 参考侧也导不出中间张量 ⇒ 换用按 block 裁剪 ONNX 的办法（更贵）。

## 5. 预算与放弃条件

- 设备 `--debug` 一轮（约 16 分钟 + 落盘）；CPU 参考一轮；二分 3~4 次拉取。
- 设备 `/data` 余量 612 GB，预估落盘 ≤ 40 GB，安全。
- 若两轮拿不到定位 ⇒ 回主线，重新评估是否该直接走"换 SoC 版本对照"
  （已有 SM8550/v73 的 `.bin`，但**缺 v73 设备**，该对照当前做不了——
  这是一个**尚未排除**的可能：v79 在本 SDK 上的支持成熟度）。

## ❌ 判据 3 触发失败 → 但**它本身定错了**，判据 1 一并作废

判据 3 要求"误差沿 Id 单调不减"，实测出现三处回落
（50→103、306→359、624→625），按原文本轮应判为"张量配错、无效"。

**但复查后确认：判据 3 的前提是错的，不是数据的问题。**

1. **Id 顺序 ≠ 数据依赖顺序**。`trace_dag.py` 读出的真实依赖是
   `unified = add_222 + mul_484`（**残差加**）、`mul_484 = tanh_33 × mul_483`（门控乘）。
   `unified`(19.47%) 低于 `mul_484`(73.14%) 是**残差路径稀释误差**的正常结果。
   `stack_28` / `add_153` / `view_125` 分处不同分支，本就不构成一条链。
2. **相对误差按各张量自身范数归一**，不同张量间不可直接比大小
   （`linear_118_fc` std=41.6 vs `mul_436` std=0.082，差 500 倍）。
3. RmsNorm 会归一化、残差会稀释，误差**物理上就应该**非单调。

⇒ **判据 1（"第一个跳变点"）与判据 3 共用"顺序性"这个错误前提，两条一并作废。**
   不得据第一轮数据宣称"引入点在 Id 区间 (103,153]"。

> **这是本项目第二次把判据的"操作化"写错**（第一次：对称量化 ⇔ offset = -128，
> 实际量化器改用有符号表示，offset = 0）。
> **教训**：判据里凡是涉及"顺序""单调""某个具体数值编码"的，
> 定稿前必须先用一个已知样本验证该操作化本身成立。

## ✅ 不依赖顺序、因而仍然成立的观察

增益 `k = <htp, cpu>/<cpu, cpu>` 是**单个张量自身的属性**，与探针顺序无关：

- **`mul_484` 处 k = 0.4077** —— HTP 只算出正确幅值的 **40.8%**
- `select_160_pre_reshape` k = 0.8609、`unified` k = 0.8465
- 前段（Id ≤ 359）的 k 全部 ≈ 1.00，**增益偏离集中在后段**

⇒ 这是**第二轮**要回答的问题：`mul_484` 的 k=0.41 是**在该乘法处产生**，
   还是从 `tanh_33` / `mul_483` **继承**而来。

## 第二轮的判据（重新定稿，替代作废的判据 1/3）

沿**真实依赖链**取点（`scripts/probes2_lastblock.py`，17 个张量、1543 MB，
覆盖 layers.14 的注意力与 FFN 两条路径）。

**判据 1′（误差放大点）**：对每个算子 X，比较其输出误差与**各输入误差的最大值**。
若 `out_err ≥ 2 × max(in_err)` **且** `out_err − max(in_err) ≥ 5 个百分点`，
判定 X 为**误差放大点**。
- 找到一个或少数几个 ⇒ 定位成功，按增量排序给出。
- 一个都找不到（每个算子增量都很小）⇒ **误差沿链路均匀累积，无单一引入算子**，
  此时**才**回到"改全局配置"，且结论须写明。

**判据 2′（形态）**：对每个放大点，报告是**增益型**（k 偏离 1）还是**噪声型**（k≈1，残差大）。

**判据 3′（有效性）**：两侧张量元素数必须一致；`unified` 必须与既有数据逐位相同。
（**不再要求单调性**——已证明该要求本身错误。）

# 第二轮执行结果（2026-08-15）：✅ **定位成功 —— 误差放大点全是 `RmsNorm`**

17 个探针沿真实 DAG 覆盖 layers.14 的注意力与 FFN 两条路径。判据 3′ 通过
（元素数一致；`unified` 与既有数据一致）。

## 判据 1′（误差放大点）

⚠️ **先修正一个检测器盲区**：初版检测器只统计"有数据的输入"，
而部分算子的输入是 `Reshape` 出来的中间名（`linear_153` 而非 `linear_153_fc`），
导致漏统计。`Reshape` 不改数值，按其上游取值后重算：

| 算子 | 真实输入误差 | 输出误差 | 倍数 | 增益 k |
|---|---|---|---|---|
| Id=606 **RmsNorm** `mul_476` | linear_150 = 54.81% | 35.59% | **0.65×（降低）** | 1.019 |
| Id=618 `silu_19` | linear_151 = 68.60%, val_2609 = 24.03% | 75.24% | 1.10× | 0.927 |
| Id=609 **RmsNorm** `mul_479` | add_222 = 16.63% | **92.15%** | **5.54×** | 0.955 |
| Id=623 **RmsNorm** `mul_483` | linear_153 = **5.68%** | **95.74%** | **16.9×** | **0.331** |

> `silu_19` 曾被初版检测器误报为放大点（漏了 68.60% 的那个输入）。
> **查过才发现，不是放大点。** 记此以免后来者照初版结论走。

**⇒ 放大点全部是 `RmsNorm`。`mul_483` 输入仅 5.68%，输出 95.74%，放大 16.9 倍。**

## 判据 2′（形态）

`mul_483` 的增益 **k = 0.331** —— HTP 只算出正确幅值的 33%，是**增益型**重灾区。
`mul_479` k=0.955 偏噪声型。

## 更简洁的刻画：RmsNorm 的输出误差与输入误差基本脱钩

| RmsNorm | 输入误差 | 输出误差 |
|---|---|---|
| `mul_476` | 54.81% | 35.59% |
| `mul_479` | 16.63% | 92.15% |
| `mul_483` | 5.68% | 95.74% |

输入 5.68% 进、95.74% 出 ⇒ **HTP 的 RmsNorm 几乎把输入误差信息抹掉，
输出一个自身固有的大误差。**

## 已验证并**推翻**的两个机制假设（记录以免重走）

### ❌ 假设 A：gamma 权重 8-bit 量化质量差 —— **反相关，推翻**

从 FP32 ONNX 取出实际 gamma 分布核对（`scripts/check_rmsnorm_gamma.py`）：

| gamma | 量程被前1%撑大 | 中位有效位宽 | 相对误差>10%的元素 | 该 RmsNorm 误差倍数 |
|---|---|---|---|---|
| `attention_norm2` | 3.5× | 5.47 bit | **25.5%** | **0.65×（降低）** |
| `ffn_norm1` | 1.1× | **7.21 bit** | **0.2%** | **5.54×** |
| `ffn_norm2` | 6.1× | 4.98 bit | 13.8% | **16.9×** |

**量化质量最好的 `ffn_norm1` 放大最多，最差的 `attention_norm2` 反而降低误差。**
⇒ 假设 A 被数据反向否定。

### ⚠️ 假设 B：`weight_bias` 的 `scale == 0` —— **普遍存在，但解释不了差异**

①实测：part1b 的 **44 个 RmsNorm，其 `weight_bias` 的 scale 全部 == 0**
（`bw=32`，`range=±0.0001`，`offset=0`）。

但**三个 RmsNorm 都有 scale=0，包括误差反而降低的 `mul_476`**
⇒ 它是共同项，**不能解释 0.65× 与 16.9× 的差异**。
可能是一个**共同的误差地板**，但需独立验证，**不得据此下结论**。

> **注意**：HANDOVER 14.18 曾以"part1a 有 71 个、part1b 有 44 个，而这两图**编译干净**"
> 为由把零 scale 判为**良性**。
> **那次排除针对的是编译期报错，不是数值正确性——"编译干净"≠"算得对"。**
> 该结论在数值维度上**从未被验证**，现予重开。

## 6. 与正在进行的对称权重实验的关系

`EXP_PLAN_SYM_WEIGHTS` 的量化仍在后台跑，**不叫停**：它是独立数据点，
跑完自然有结果。但**它不再是主线**——
本方案（定位）的结论优先，若定位指向某个具体算子，
对称权重实验的结果只作为旁证解读，**不得反过来当作根因结论**。
