## 二、总目标与验收（顶层）

**目标**：在**不新增设备存储/下载量级成本**、**不击穿 PD 红线（3.3 GB，#57）**、
**不抬高运行时 ION 峰值**（当前 app 内峰值 9100 MiB、余量仅 839 MiB，见 #145/F）的前提下，
支持 ≥2 个输出比例。

**总验收（四条全过才算路线 D 成立）**：
1. **体积**：N 个比例的多图 context ≤ 1.3 × 单图 context（权重确实共享）
2. **PD**：设备上 `createFromBinary` 不返回 `0x3ea`（#57 的容量上限错误码）
3. **ION**：`ENABLE_GRAPHS` 只启用一个图时，ION 占用 ≤ 1.15 × 今天同段的 ION
4. **精度**：1:1 那个图的出图 sha256 与今天**逐字节相同**（零精度代价，同 F 的 G3）

任一条失败 ⇒ 路线 D 关闭，理由与证据写进台账 #86。

### 阶段 0（零设备，分钟级）—— 用**已知样本**验证机制本身

**为什么必须有这一阶段**：约束 8 要求「判据的操作化先用已知样本验证」。
本项目已因跳过这一步返工三次。这里的"操作化"是
**「体积差 ⇒ 权重是否共享」** 与 **「哪个宿主能真正产出共享」**，两者都必须先证明可判别。

**样本**：`/d/ZImage_Work/p0_experiments/p0b/actcal/q_minmax.dlc`（14.07 MB，单 FC 层，有真实权重）。
需要造出**两个图名不同、权重相同**的 DLC（记为 `A`、`B`）。

**六臂**（同一对 A/B，只变宿主与开关）：

| 臂 | 宿主 | `--dlc_path` | `weight_sharing_enabled` |
|---|---|---|---|
| W1 | Windows | A | — |
| W2 | Windows | A,B | false |
| W3 | Windows | A,B | true |
| L1 | WSL-Linux | A | — |
| L2 | WSL-Linux | A,B | false |
| L3 | WSL-Linux | A,B | true |

**事前锁定的判据**（`S(x)` = 该臂产物字节数）：

- **G0-a 双图确实编进去了**：W2/W3/L2/L3 的 `qnn-context-binary-utility` 输出里
  **恰好两个 graph 条目**，图名与 A/B 一致。不满足 ⇒ 装置错误，本阶段结论作废（不是"共享失败"）。
- **G0-b 共享生效的判据**：`S(共享臂) − S(单图臂) < 0.30 × S(单图臂)`
- **G0-c 共享未生效的判据**：`S(共享臂) / S(无共享臂) > 0.95`（即开关没起作用）
- **G0-d 宿主判决**：
  - 若 `L3` 过 G0-b 且 `W3` 过 G0-c ⇒ **F5① 属实，建图必须迁到 Linux**
  - 若 `W3` 也过 G0-b ⇒ **F5① 在 2.48 上已放宽**，Windows 可继续用（此时必须在台账里
    显式标注「与官方文档冲突，以实测为准」，并保留文档原文）
  - 若 `L3` 与 `W3` 都过 G0-c ⇒ **共享开关在本 SDK 上整体无效** ⇒ 路线 D 当场关闭
- **G0-e 报错行为**：记录 W3 是报错 / 告警 / 静默三者中的哪一种（回答 §1.2 的③）

**前置**：F7 的 `libc++.so.1` 缺失必须先解决，否则 L1/L2/L3 跑不了。

**成本**：建 6 个 ~15 MB 的 context，预计每个 1~3 分钟 ⇒ **≤ 30 分钟，零设备**。

**方向错 vs 执行错的区分（R1）**：本阶段自带空白对照（W2/L2 = 无共享），
因此"体积没降"可以被明确归因到「开关无效」而非「装置错误」。

### 阶段 1（零设备，小时级）—— 真段双图，测体积

**前置**：阶段 0 的 G0-d 给出可用宿主。
**前置缺口**：③ 目前盘上**没有** 4:3 的量化 DLC（路线 A 的 14.7 GB 已回收）。需先重做该比例的
ONNX 手术 + 量化。

🔴 **为什么共享权重之后仍然必须逐比例建 DLC（2026-08-31 用户提问后补写，防止后来者误以为可以省掉）**：
权重共享**去重的是权重副本，不解除「每个形状要有自己的图」**。
① HTP 要求**静态形状**（路线 B 已据此关闭）⇒ 每比例必须有独立编译的图 ⇒ 必须有独立 DLC。
① #86 引的 AI Hub 原文同向：*"both inputs will need to be **traced separately**"*。
⇒ 共享买到的是 `5×(权重+调度)` → `1×权重 + 5×调度`，这正是它区别于路线 A（每比例 6.8 GB）的全部价值。

🟢 **配方收紧（同日）：4:3 臂必须用 `--quantization_overrides` 复用 1:1 臂的权重 encoding**（#45 已打通通路）。
两条理由：
① **正确性**：共享的前提是两个图引用**同一份权重**；若两臂量化权重字节不同，就没有东西可共享。
　⚠️ ③**「权重量化与形状无关故天然相同」是预期、不是实测** —— 复用 overrides 可把该风险直接归零，不必赌。
② **成本**：这样重量化几乎零成本，原先"成本未估准"主要来自误以为要重跑完整校准。
⚠️ 仍不得沿用 #134 的「0.1 分钟/段」——那是 seq 手术，不是换空间形状；**真实成本仍以实测为准**。
⚠️ 用 overrides 必须显式带 `--float_bitwidth 32`（#46：否则浮点位宽被默认降到 FP16，单变量被破坏）。

**做法**：取**一段**（建议 part1b，四段里工具链最全、#147 已有它的 CTRL 基线），
建 `1:1 + 4:3` 双图共享 context。

⚠️ **自审第 2 条（约束 9）**：选 part1b 的理由是"工具链最齐"，
这**正是我上次犯错的理由**（"优化了最方便测的，不是最该修的"）。
此处可接受，**因为阶段 1 只测体积/可建性，不做归因也不做优化决策** —— 换段不改变结论性质。
但**阶段 2 必须用真正的部署段集合**，不得只测 part1b 就外推。

**事前锁定的判据**：
- **G1 体积**：`S(双图共享) ≤ 1.30 × S(单图部署版)`。不过 ⇒ 关闭路线 D。
- **G1-b 装置画像**：`check_ctx_identity.py --expect-arch 79 --expect-vtcm 8`（§7.2 硬规则，#95/#96）。
  不过 ⇒ 本阶段结论作废重做。
- **G1-c** `qnn-context-binary-utility` 读出的 `spillFillBufferSize`：记录数值（供 #146 与 ION 预算用），
  **不设判据**，只做观测。

## 六、阶段 1-A：ONNX 比例手术（2026-09-02 定稿，判据事前锁定）

### 6.1 目标与几何

把四段 ONNX 从 `1024×1024`（latent 128×128，网格 64×64，4096 tokens）改到目标比例。
`tokens = (H/16)×(W/16)`；精确比例且 latent 双偶 ⇒ 首批做 **4:3 = 1152×864**
（latent 144×108，网格 **72×54**，**3888 tokens**，`unified = 80+3888 = 3968`）。

### 6.2 要改什么（①全部实测自 `transformer_part*_clip_L80.onnx`，非推导）

| 段 | 对象 | 现值 → 新值 |
|---|---|---|
| part1a | 输入 `latents` | `[1,16,128,128]` → `[1,16,108,144]` |
| part1a | `stack_1`（图像位置 ID，int32） | `(1,64,64,3)` → `(1,54,72,3)`；**轴0 恒 33 原样保留**，轴1=行号、轴2=列号（已逐点核对是标准 meshgrid） |
| part1a | `val_70`（patchify 重排） | `[16,1,1,64,2,64,2]` → `[16,1,1,54,2,72,2]` |
| part1a | `latents_shape` | `[1,128,128]` → `[1,108,144]` |
| part1a | `unsqueeze_3`（bool，**实测全 False**） | `(4096,1)` → `(3888,1)` 全 False |
| part2b | `shape_120_fixed`（unpatchify） | `[1,64,64,1,2,2,16]` → `[1,54,72,1,2,2,16]` |
| part2b | `shape_unsafe_fixed` | `[1,16,128,128]` → `[1,16,108,144]` |
| part2b | `slice_1_end_4096` | `4096` → `3888` |
| 四段 | 一切含 `4096` / `4176` 的形状常量 | `4096→3888`、`4176→3968` |

**不动**：RoPE 频率表 `mul_5/63 [1536,16]`、`mul_7/9/65/67 [512,24]`（①实测按 512 位置满容量烘焙，
72/54 完全落在表内）；caption 侧一切 80 相关；`attention.norm_q/k.weight [128]`（head_dim，
①已确认是 3840/30 的假阳性）。

### 6.3 🔴 撞值风险（#134 踩过同一个坑，方向相反）

`dit_seq_surgery.py` 文件头记：`32×128 = 4096` 与图像 token 数**撞值**，当时逐个追消费者后
判定「所有含 4096 的常量都在图像流 ⇒ 一律不动」。**本次方向相反，那批常量恰恰全要改。**
⇒ **必须复用同一套逐消费者核对**，且新增两个撞值检查：
- `3888` 是否与任何既有常量撞值（如 head_dim 的倍数）
- `54 / 72` 是否与 `30`（头数）、`64`（axes_dims/2）、`128`（head_dim）产生歧义

### 6.4 判据（**执行前锁定**）

| 门 | 内容 | 不过怎么办 |
|---|---|---|
| **S1 结构** | 四段 `onnx.checker` 通过；`shape_inference` 无冲突 | 修手术，不得放行 |
| **S2 接缝** | 段间张量形状**逐对相等**（part1a 出 = part1b 入，依此类推），且都等于新的 3968 | 同上 |
| **S3 常量全覆盖** | 手术后全盘扫描：**不存在**仍含 `4096` 或 `4176` 的形状常量 | 说明漏改，回 6.2 补 |
| **S4 无误伤** | `80`（caption）、`3840`/`128`/`30`（模型维度）相关常量**逐个未变**；RoPE 频率表**逐字节未变** | 同上 |
| **S5 张量名不变** | 手术前后张量名集合**完全相同** ⇒ §29.8 的 Clip+FP16 白名单继续适用（#134 的关键性质） | 若变，白名单失效，须重做 |
| **S6 数值** | ORT 跑 FP32 前向，输出 `latents` 形状 = `[1,16,108,144]`，且**无 NaN/Inf** | 同上 |

⚠️ ③**S1~S6 全过也不证明画质**。画质要等量化 + 建图 + 设备实测（阶段 3）。
本阶段只保证「结构正确、单变量干净」。

### 6.5 与已有工具的关系
