# EXP_PLAN_S32_VS_FP32 —— 32 槽 TE 是离原始模型更近还是更远

**定稿**：2026-08-27（**判据在跑之前锁定，不得事后修改**）
**缘起**：Tier 1 交付后 T3（新旧量化版逐字节相同）失败。复查确认 **T3 判据本身无效**
（见 `EXP_PLAN_PROMPT_LEN.md` §十：位置索引张量量程必然 19→31，结构上不可能相同；
且拿「上一个量化版本」当基准违反 `MAINLINE §2.1.1`）。
⇒ 唯一有意义的问题是：**相对 FP32 参考**，新版更近还是更远。

---

## 一、必须先讲清的边界（防止双方朝有利方向解读）

| prompt 长度 | 32 槽是否有语义优势 |
|---|---|
| **正文 ≤ 12 token** | ❌ **没有**。多出的槽本来就会被 `cap_pad_mask` 换成 pad embedding，新旧下游相同。差异**纯粹是重量化噪声** ⇒ 更近/更远是**掷硬币** |
| **正文 > 12 token** | ✅ **必然更近**，因为旧版直接丢了尾巴（用户那句 29 token 的旧版丢 9 个） |

⇒ **本实验测的是第一种**（`一条蓝色的鱼`，12 token 含模板）。
它回答的是：「**重量化本身有没有伤害画质**」，而不是「长 prompt 是否更好」——后者是定义上的。

## 二、装置

| 臂 | 内容 | 来源 |
|---|---|---|
| **A 参考** | 我们的 **FP32 ONNX** 全链路（FP32 TE + FP32 transformer + FP32 VAE） | 现跑（`fp32_step_runner.py`） |
| **B 旧** | app 输出，**20 槽 TE** | 已有：`history id=46`（08-26 21:39） |
| **C 新** | app 输出，**32 槽 TE** | 已有：`history id=48`（08-27 20:33） |

**共享**：prompt `一条蓝色的鱼`、seed `1592868847`。
🔴 **初始噪声必须用 app 的 `std::mt19937`**（`cxx_latents.py --seed 1592868847`），
**不得用 numpy PCG64** —— 否则是同一模型的不同采样，像素比较无意义（台账 #74）。
`cxx_latents.py` 的 MT19937 测试向量自检已通过，且该脚本此前与真机对拍验证过。

⚠️ **口径说明**：A 用 FP32 TE/VAE，B/C 是 app 的全量化链。
⇒ 本实验量的是**用户实际经历的整条链** vs FP32 参考，这正是要回答的问题；
但**不能**据此归因到 TE 单独一段。

## 三、判据（**事前锁定**）

主判据 = **L3 图像 PSNR vs 臂 A**（与 `MAINLINE §2.5` 同口径，可与 11.93 / 18.67 dB 对齐）。

```
Δ = PSNR(C) − PSNR(B)
```

| Δ | 判读 |
|---|---|
| **≥ +0.2 dB** | 🟢 32 槽**更接近** FP32 |
| **abs(Δ) < 0.2 dB** | ⚪ **无法区分**（噪声级）⇒ 重量化既没帮忙也没伤害 |
| **≤ −0.2 dB** | 🔴 32 槽**更远** ⇒ 重量化有代价，需权衡「+12 token vs 画质」 |

0.2 dB 的来源：本项目已交付的两次改动量级分别是 **+3.14 dB**（#111）与 **+3.60 dB**（#106），
0.2 dB 约为其 1/16，足以把「有效果」与「噪声」分开。

⚠️ **样本量 n=1**（单 prompt 单 seed）。**不得外推到其他 prompt**。
本项目已因单样本外推栽过（#131：强/弱 prompt 各 1 个样本，改进幅度差 3.8 倍）。

## 四、失败/无效的判定

- 若臂 A 的生成失败或中途 OOM ⇒ **实验无效**，不得用部分结果下结论
- 若 B、C 的 PNG 尺寸/seed/prompt 与记录不符 ⇒ 装置错误，重取
- 🔴 若 Δ 落在 ±0.2 dB 内，**结论就是「测不出差别」**，
  **不得**改口说「略好」或「略差」——那是把噪声当信号（约束 7）

## 五、成本

约 35~45 分钟宿主时间（FP32 每步约 246 s × 8，每步独立进程避免内存累积），**零设备占用**。

## 六、结果（2026-08-27，按 §三 判据机械判读）

### 6.1 装置自校验（先确认参考臂没搭错）

臂 B（20 槽，即交付前的配置）对 FP32 参考 = **18.763 dB**，
与 `MAINLINE §2.5` 记录的当前最优 **18.67 dB** 相差 0.09 dB。
⇒ **参考臂构造正确**（同口径、可与项目既有数字对齐），结果可信。

### 6.2 主结果

| 臂 | vs FP32 参考 |
|---|---|
| **B 20 槽** | **18.763 dB**（相对 L2 33.30%） |
| **C 32 槽** | **17.486 dB**（相对 L2 38.57%） |

```
Δ = PSNR(C) − PSNR(B) = −1.276 dB
```

⇒ 🔴 **判读：32 槽更远。** 超出 ±0.2 dB 阈值，是真实倒退，不是噪声。

量级参照：本项目两次有效改动分别是 **+3.14 dB**（#111）与 **+3.60 dB**（#106）
⇒ **−1.28 dB 约等于吃掉其中一次改动的 40%**，不可忽略。

### 6.3 判读纪律

- ⚠️ **n=1**（单 prompt 单 seed）。#131 已证改进幅度强烈依赖 prompt（强/弱差 3.8 倍）
  ⇒ **不得外推**「所有短 prompt 都会掉 1.28 dB」。
- ✅ 但**方向**是明确的：这个 prompt 上，重量化**确实有代价**，
  与我事前说的「掷硬币」一致 —— 硬币这次是反面。
- 📌 **长 prompt 的收益不需要测**：旧版把 29 token 的 prompt 丢了 9 个，
  是**定义上**的偏离；T4 图上「红色露肩毛衣」出现即为证据。

### 6.4 ③ 未验证的改进方向（有具体机制，不是碰运气）

**我的校准方式与运行时分布不匹配**：
`te_s32_calib.py` 把中间层 hidden 的第 12~31 槽用**复制最后一行**补齐，
而运行时那些槽装的是**真实 pad token 的 hidden state**（`kQwenPadId=151643`）。

⇒ 可用**真实分布**重做校准：现在已有能跑 FP32 TE 的手段
（`te_s32_fp32_probe.py` 的 ORT 路径），可直接生成 seq-32 的真实中间层激活。
成本：重量化约 20 秒/段、建 context 约 10 秒/段 ⇒ **宿主几分钟**，加一次设备验证。

⚠️ **这是假设，不是结论**：无法保证能补回 1.28 dB，
因为位置索引张量量程 19→31 是**结构性的**，那部分改不掉。

## 七、🚫 我的「pad 行污染量程」断言已被推翻（2026-08-27，用户要求核查后）

**我说过**：「seq 从 20 加到 32，多出来的 pad 行本身就会污染 per-tensor 量程，
这是 per-tensor 量化 + 更长序列的固有代价」。**这是断言，没有证据。三条独立检查都不支持它。**

### 7.1 直接实测：pad 行**完全没有**撑宽量程

用 v2 的真实校准数据，比较「只统计真实行」与「统计全部 32 行」的量程：

| 张量 | 真实行量程 | 含 pad 行量程 | 撑宽比 |
|---|---|---|---|
| `add_2452` | [−4602.504, 16133.094] | [−4602.504, 16133.094] | **×1.0000** |
| `add_4828` | [−4596.507, 16391.750] | [−4596.507, 16391.750] | **×1.0000** |
| `add_7204` | [−4582.164, 16388.350] | [−4582.164, 16388.350] | **×1.0000** |

⇒ **极值全部由真实 token 决定，pad 行一点贡献都没有。**

### 7.2 v1/v2 的差异另有来源

两版唯一的输入差别是 **pad 用的 token id**（v1 用 `0`，v2 用运行时的 `151643`）。
实测二者 embedding 量级相近（|max| 0.0806 vs 0.0962；L2 1.079 vs 0.994）
⇒ 差异是**换 token 后逐层累积的小扰动**（196 个 encoding、量程中位数 ×1.03），
**不是「序列变长的固有代价」**。

### 7.3 外部证据（用户要求：不得直接断言）

- **QAIRT 官方文档**（`QNN/general/quantization.html`）：
  *"a representative set of input data needs to be used"*
  ⇒ 校准集应代表**实际推理输入**。全文 **"pad" 命中 0 次**，官方未把 padding 列为风险项。
- **文献**：LLM 的极端激活集中在**特殊 token 与靠前位置**
  （"most LLMs exhibit massive activations at initial token positions"），
  而这些位置在 seq 20 与 seq 32 下**完全相同** ⇒ 与我 7.1 的实测一致。
- **实践共识**：校准序列长度应"representative of typical inference scenarios"
  ⇒ **支持 v2（与运行时一致），不支持 v1。**
- ❌ **没有**任何来源主张「padding 越多量化越差」。

### 7.4 因此，v1 那 −1.276 dB 的原因**仍未查明**

已排除：pad 行撑宽量程（7.1 实测否定）、序列长度固有代价（7.3 无来源支持）。
剩余候选（**均未验证**）：
① 位置索引张量量程 19→31 —— 但 16-bit 下步长远细于整数间隔 1，**机制上应无害**；
② 483 个中位数仅 0.025% 的微小 encoding 漂移经 8 步扩散被放大；
③ **两个近似量化版本之间本来就有约 1 dB 量级的随机差异**（`MAINLINE §2.1.1` 的推论）
   —— 若 v2 落在 18.7 dB 附近，则 ③ 成立、v1 的 17.49 只是抽样；
   若 v2 也在 17.5 附近，则 ③ 不成立，是 32 槽的系统性代价。

**v2 的实测正好能区分 ② ③。**

## 八、v2 结果与因果闭环（2026-08-27）

### 8.1 三版对同一张 FP32 参考

| 版本 | PSNR | Δ vs 20 槽 |
|---|---|---|
| **B 20 槽（部署前）** | **18.763 dB** | — |
| C 32 槽 v1（复制最后一行校准） | 17.486 dB | **−1.276** |
| **D 32 槽 v2（真实分布校准）** | **17.025 dB** | **−1.738** |

⇒ 🔴 **两个独立校准方式都落在 17.0~17.5，均显著低于 18.76。**
候选 ③（「两个近似量化版本本来就有 ~1 dB 随机差异」）**不被支持** ——
若是随机抽样，不该两次都偏向同一侧。
⚠️ 且**按官方/文献建议做的 v2（匹配运行时分布）反而更差**，与预期方向相反。

### 8.2 图层面已被完全排除（实测闭环）

| 检查 | 结果 |
|---|---|
| FP32 part1 输出，真实 token | **逐位相同**（最大差 0） |
| FP32 **整条 TE 链**的 `caption`，真实槽 `[0:12]` | **逐位相同**（最大差 0） |
| `caption` 在 part1a 的下游 | `Gather → Pow → ReduceMean(**axes=[-1]**, 逐 token) → Mul → cap_embedder`，之后 `where_1` 用 `cap_pad_token` 替换 pad 槽 |
| ⇒ pad 槽内容（FP32 下最大差 127.8）对真实槽的影响 | **无**（归约轴只有隐藏维，且随后被整体替换） |

⇒ **图的数学在 FP32 下完全等价 ⇒ 1.738 dB 全部来自量化。**

### 8.3 机制（②由实测推出）

TE 的**内部** encoding 因校准数据形状改变而漂移（部署版 vs v1：753 个里 487 个不同）。
per-tensor 量化是逐元素的，pad 行**不能**在推理时影响真实行；
但**校准阶段**内部张量（注意力矩阵等，形状随 seq 变化）的统计确实变了
⇒ 真实行经过的每个 scale 都略有不同 ⇒ caption 的真实槽被量化成不同的值
⇒ 8 步扩散放大 ⇒ 成图差 1.7 dB。

### 8.4 🟢 未试的针对性方案（直接冲着 8.2/8.3 的结论去）

既然 **FP32 下真实槽逐位相同**，问题只在「重量化扰动了它们」，
那就**别重新标定**：用 `--quantization_overrides`（#45，本项目已打通）
把**部署版 20 槽的 encoding 注入 32 槽的图**。
⇒ 真实行的 scale 与部署版完全一致 ⇒ 短 prompt 应当**精确回到 18.763 dB**。

⚠️ **必须排除的一类张量**：量程随 seq 合法变化的（位置索引 `_to_copy_1` 等，0..19 → 0..31）。
直接套用旧 encoding 会把槽 20~31 的位置索引**钳掉** ⇒ 短 prompt 无碍、**长 prompt 会坏**。
⇒ 正确做法是**只覆盖量程与 seq 无关的张量**，让 seq 相关的那几个重新标定。

成本：量化 20 秒/段、建 context 10 秒/段 ⇒ 宿主几分钟 + 一次设备验证。
③**未验证**：能否精确回到 18.763，取决于「量程与 seq 无关」这个筛选是否干净。

## 九、v3 结果与三次尝试的规律（2026-08-27）

| 版本 | 校准方式 | 量程漂移中位数 | >1% 张量数 | **PSNR** |
|---|---|---|---|---|
| **20 槽（部署版）** | 原始 | — | — | **18.763** |
| 32 槽 v1 | 复制最后一行 | 0.0251% | 66 | 17.486 |
| 32 槽 v2 | 真实 pad token | 0.0478% | 164 | 17.025 |
| 32 槽 v3 | 满槽无 padding | 0.1342% | 271 | **16.024** |

⇒ **单调：离部署版 encoding 越远，画质越差**（n=3，方向完全一致）。

**张量级机制被验证过一次**：v2 里 `linear_32` 量程 ×2.05（被 pad 行撑爆），
v3 改用满槽校准后回到 16.299（部署版 16.360）⇒ 该张量修好了。
**但整体反而更差** —— 因为 v3 扩写 prompt 时**连内容一起改了**，不是干净的单变量，
换语料带来的全局漂移（271 个 >1%）盖过了单张量的修复。

### 9.2 仍未回答的

## 十、🔴 根因调查：我之前的机制解释**被直接测量推翻**（2026-08-27）

用户质疑「到底有没有好好找原因」——**确实没有**，前三轮是在换校准配方然后上机采样。
本节是补做的直接测量。

### 10.1 工具：TE 的 QDQ 模拟（`scripts/te_qdq_sim.py`，零设备）

在 FP32 ONNX 上按各版本 encoding 插 quantize-dequantize，直接量
**「量化后的 caption 相对 FP32 的误差」**——即 TE 唯一向下游输出的东西。

**先做工具自检（约束 8）**：
- 自检1 确定性：同一图跑两次逐位相同 ✅
- 自检2（第一版**构造错误**）：缩小 scale 同时放大 offset ⇒ 量程整个塌掉，报 5466% ⇒ **该自检无效，非工具缺陷**
- 自检2（订正后）：只对 `caption` 插一处 QDQ，与 numpy 参考实现
  `sc*clip(round(x/sc), off, 65535+off)` 比对 ⇒ **最大绝对差 0，逐位相同** ✅
  单张量量化误差 0.1030%（小而非零，合理）

### 10.2 结果：**32 槽的 caption 误差反而更小**

12 个 prompt（均 ≤20 token，两种槽数下都不截断）：

| 版本 | caption 相对误差 中位数 | 均值 | 逐 prompt 最优次数 |
|---|---|---|---|
| **20 槽（部署版）** | **3.5988%** | 3.6183% | **1 / 12** |
| 32 槽 v1 | 3.4528% | 3.4341% | 4 / 12 |
| **32 槽 v3** | **3.3956%** | **3.3803%** | **7 / 12** |

⇒ 🚫 **「encoding 漂移 ⇒ caption 变差 ⇒ 成图变差」这条机制被推翻。**
TE 的量化质量在 32 槽下**没有变差，还略好**。

### 10.3 用户实测提供的关键反例

同一改动（20 槽 → 32 槽 v3）在两个 prompt 上：

| prompt | 20 槽 vs 32 槽 v3 |
|---|---|
| `一条蓝色的鱼` | **16.03 dB**（明显不同） |
| **`刘亦菲`** | **21.65 dB**（用户肉眼判定「一样」） |

⇒ 同一改动的可感知度差 **5.6 dB**，与 #131 记录的规律一致：
**prompt 钉死的收敛，没钉死的自由度都会变。**

### 10.4 现在的解释（②由①推出）与仍未验证的部分

- ①caption 误差**量级**几乎不变（3.40% vs 3.60%），但**方向**是不同的量化噪声实现
- ①成图差异强烈依赖 prompt 约束强度
- ⇒ ②「一条蓝色的鱼」上那 −2.7 dB，**很可能是噪声方向在这个弱 prompt 上落得不利**，
  而不是系统性的质量损失
- ⚠️ ③**仍未验证**：caption 误差是**代理量**，#121 已证 L1 不能预测 L3
  ⇒ 「caption 略好」**不等于**「成图更接近 FP32」。要断言需多 prompt 的 L3 实测。

🔴 **方法论教训**：我用**一个弱 prompt、n=1** 判决「32 槽是否更差」，
功率不足；#131 早就写着 prompt 依赖极强。这是实验设计缺陷，不是数据问题。
